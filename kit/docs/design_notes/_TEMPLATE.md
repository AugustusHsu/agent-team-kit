# [DN-0XX] 一句話講清楚「要決定什麼」

**🚥 狀態 (Status):** 🌱 Seed
**📅 建立 (Created):** YYYY-MM-DD
**🔗 依賴 (Depends on):** DN-0YY（寫清楚要等它定案的是哪一點）／無
**📌 來源 (Origin):** 必填——使用者指令（日期）／Icebox 第 N 項／某工單寫不出 AC 而卡住
**🤝 姊妹篇 (Sibling):** 必須**同時**設計、不分先後的 DN；沒有就寫「無」

⚠️ **DN 不得寫實作步驟。** 本檔只比方案、列待決事項。
一旦開始寫「第一步做什麼、第二步做什麼」，代表設計已經收斂——
該做的是畢業並開工單，不是把 DN 寫成第二套工單系統。

## 1. 問題陳述

現在**實際**哪裡不對？用可驗證的事實描述，不要用「不夠好」「有點亂」。
好的問題陳述會讓「什麼算解決了」變得明顯。

## 2. 既有事實

盤點現況：既有的檔案、規範、資料，以及**實際跑過的觀察**。
把「我以為」跟「我查過」分開寫——後者要附指令或檔案路徑，讓別人能重跑。

## 3. 已定調的設計

**只寫已經拍板、不會再翻的部分。** 還在比較的放 §4。
每一條都要能回答「為什麼不是另一種做法」。

## 4. 待決事項

| # | 待決 | 選項 | 建議 |
|---|---|---|---|
| 4.1 | | | |

每一項都要有**建議＋理由＋反方**，最後由使用者拍板；
裁定下來就用引用區塊就地記在該項底下，不要另開一節：

> ✅ **裁定（YYYY-MM-DD）：** ……

延後處理的項目要寫明「延後至 DN-0YY」——延後也必須有去處，不能只是不寫。

## 5. 畢業去向（畢業時才填）

**結論落不到第 1 層文件，對 Agent 而言等於不存在。**
填「哪一份第 1 層文件會被改」＋「開出哪幾張工單」，去向分類見
[`../standards/documentation_conventions.md`](../standards/documentation_conventions.md)。

畢業當下同時要做兩件事：頂端狀態改 `🎓 Graduated`，並在標題底下加一行

```
> 🎓 已畢業（YYYY-MM-DD）→ {工單號}。本檔凍結，不再更新。
```

## 📎 填寫指引（寫完可以整段刪掉）

### 狀態

```
🌱 Seed ──→ 🔍 Exploring ──→ 🎓 Graduated（工單已開出）
                         └─→ 🚫 Dropped（決定不做，理由必填）
```

| 狀態 | 含義 | 誰推進 |
|---|---|---|
| 🌱 Seed | 檔案剛建，只有問題陳述，沒人在推 | scrum-master |
| 🔍 Exploring | 正在比方案，「待決事項」清單成形中 | system-architect / tech-lead |
| 🎓 Graduated | 工單已開出，本檔凍結唯讀 | **使用者簽核** |
| 🚫 Dropped | 決定不做，理由必填，本檔凍結唯讀 | **使用者簽核** |

**刻意不重用工單的五狀態**：工單狀態回答「事情做完了沒」，DN 回答「問題想清楚了沒」。

### 畢業條件（三條全中才算）

1. **「待決事項」每項都有答案**，或明確標記「延後至 DN-0YY」。
2. ⭐ **寫得出至少一張工單的驗收標準。** 寫不出可驗收的 AC ＝ 設計沒收斂完，不准畢業。
3. **使用者本人簽核。** 這一類決定不外包給 AI。

第 2 條是主力：它把「想清楚了沒」這種主觀感覺換成當場可驗證的動作，
也防止 `🔍 Exploring` 變成無限期停車場。

### 長度

軟上限 **250 行**。超過不是違規，是觸發一次檢查：

1. 裝了不只一個待決問題？→ 拆成多份 DN。
2. 已經夠寫 AC 了？→ 畢業。

兩題都否就在文中註明「已檢查」繼續長。行數本身判不了好壞。
