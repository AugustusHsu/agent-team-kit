## 2. AC-05：廢除表判定「不加列」，四項理由

`CLAUDE.md` 要求「**推翻**既有流程規範時」登記。本輪逐條檢視後判定沒有推翻：

| # | 理由 | 依據 |
|---|---|---|
| 1 | **四處改動都是加條件式但書，不是反轉** | 「一張工單一行」在單線情境下仍然**完全成立**，只是不再被當成無條件命題。原句一個字都沒被刪 |
| 2 | **形狀 E 特意保住了 §6.4 的語意** | 真正的反轉是形狀 C 才有的：`branch -d` 從「= Done」變成「= 輪次已合併」。改採 E 之後 §6.4 一個字都沒動，`branch -d` **逐張**仍成功（§5 實測） |
| 3 | **沒有殘留可抓** | 廢除表防的是「散落在別處、沒人想到要改」的舊敘述。實查：`grep -rn '一張工單一行' kit/` 只有 `git_workflow.md` 四處，全部已加但書或位於 §7 內；`team_protocol.md`、十三份 SKILL.md、evals.json **零命中** |
| 4 | **硬加會製造誤判** | 若加一列 regex 抓「一張工單一行」，它會命中 §4 與 §6.1 那兩處**正確的、帶但書的**敘述——正是測試 docstring「邊界二（誤判）」描述的情形。加了會讓測試變成噪音，反而降低這道防線的可信度 |

> 📌 這個判定**綁定形狀 E**。若日後改採形狀 C（輪次分支取代逐張分支），
> §6.4 的 `branch -d` 語意就會真的反轉，屆時必須回來補這一列。

**這段同時證明三件事**：主線只有一顆 merge（§7.1 成立）、`--first-parent`

也就是 §2 理由 2 的實據）。

### 5.2 合併訊息的三種查詢對照

```
=== A. git log --oneline --first-parent（看這輪有哪些工單）===
af43fa8 🔧 merge(round): [PEV-DEV-AGENT-030／029／025] 本輪三張工單
afdd78e base

=== B. 用完整 ID 反查 merge commit：git log --grep=PEV-DEV-AGENT-029 ===
af43fa8 🔧 merge(round): [PEV-DEV-AGENT-030／029／025] 本輪三張工單

=== C. 對照：第一行縮寫時 --oneline | grep 完整 ID 找不找得到 ===
  找不到 <<< 所以 Body 的完整 ID 是必要的，查詢要用 --grep

=== D. 側支逐張可見 ===
6431519 refactor: [PEV-DEV-AGENT-025] skill 盤點
e35d649 fix: [PEV-DEV-AGENT-029] 移除硬編碼
ac0e74b fix: [PEV-DEV-AGENT-030] 取號改從檔名取
```

**C 段是 §7.3 存在的理由**——它證明「Body 要列完整 ID」不是格式潔癖：
第一行縮寫後，慣用的 `--oneline | grep <TaskID>` 會**查無此工單**，
只有 `--grep` 走得通，而 `--grep` 要有效就必須靠 Body 的完整 ID。
規範若只寫「第一行可以縮寫」而不寫這一條，工單就會變成查不到的孤兒。
