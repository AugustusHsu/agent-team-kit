### ⚠️ 對照 2 第一版沒有轉紅

`test_README_內容物涵蓋出貨的腳本與目錄` 的初版是拿**整份 README** 做子字串比對。
刪掉樹裡的 `precheck.py` 之後測試仍然綠燈——因為我在同一次修改中，
於 `.github/workflows/kit-precheck.yml` 那一行的註解寫了「在 CI 上跑 `precheck.py`」，
**正文的順口提及把樹裡的缺漏遮掉了**。

修正：測試改為只掃「## 內容物」底下那個 fenced block（`_內容物樹()`），
同時把該行註解改成不重複檔名。修正後 2／2b／2c 三個方向全部轉紅。

這件事本身就是負向對照的價值證明：**不做這一步，這個測試會以「已經有測試保護」的
名義存在，卻抓不到它唯一該抓的東西**——正是 `design_note.md` §2 第 2 類（宣稱 ≠ 實際）。

## 5. 設計判斷

**AC-04「不重複正版內容」與 AC-01「要有表格」是互相衝突的**，不可能兩全：
摘要一張表就是製造第二份表述。這件事 repo 自己有前例——`5f844242` 記載
`docs/standards/team_protocol.md` 的拷貝「已與正版分岔 53 行」。

所以解法不是假裝沒重複，而是**把重複變成受檢查的重複**：README 只抄「列名」
（能力清單），欄位內容自然是濃縮版，再用測試斷言列名與 §8.1 逐字相同。
這與 `019` 的做法一致（`test_能力對照表的檢查內容與_precheck_實際項目一致`），
也與 `test_指路檔章節索引與正版同步` 是同一個模式。**kit 允許第二份表述，但必須可驗證。**

**為什麼 (b)「有遠端但不開 PR」不列成第四欄。**
它的七項 git 能力有六項與 GitHub 欄完全相同（branch、Actions、branch protection…），
唯一不同的是審查載體。列成一欄會有六格重複，讀者反而看不出差異在哪。
改用正文一句話點出差異與那個實際踩過的坑（只監聽預設分支的 workflow 在工單分支等於沒跑）。

## 6. 已知落差（不在本單處理）

- **這三個測試不出貨。** `tests/` 不會被安裝，所以使用者專案的 README 沒有同等保護。
  要出貨得做成 precheck 的檢查項，但「README 該有哪張表」是本 repo 專屬的約定，
  不適合強加給所有專案。維持現狀。
- **`precheck.check_dead_links()` 只掃 `docs/`。** 本單用測試補上了本 repo 的 README，
  但使用者專案的根目錄 markdown 仍在檢查範圍外。要不要放寬掃描範圍
  （並排除 `node_modules` 等）沒有結論，留給 `PEV-DEV-AGENT-022` 之後再議。
- **`Closed` 留空不會被任何檢查抓到。** 本單結案時我一度把 `Status` 改成 `Done` 卻沒填
  `Closed`，`precheck.py` 四項檢查全綠、`exit=0`。這是 `PEV-DEV-AGENT-022` 要補的
  第一項新檢查，此處記為它的第二個真實案例（第一個是 `KIT-DEV-AGENT-001`）。
- **`_表格第一欄()` 只比對第一欄。** 欄位內容（GitHub／GitLab 各填什麼）若與正版分岔，
  測試抓不到。比對整張表會讓 README 無法濃縮，取捨後選擇只鎖列名。
