## 4. 設計判斷

**為什麼 `Closed` 填 `2026-08-16T15:05+08:00` 而不是清帳當天。**
那是 KIT-001 最後一次實質變更的 commit（`cd0e1ff`）時間。填清帳當天會讓
`git log` 與工單完成時間對不上，且會捏造出「這件事做了三天」的假象。
補的是帳，不是工作。

**為什麼不補 `reviews/KIT-DEV-AGENT-001.md`。**
審查檔是 `PEV-DEV-AGENT-016` 之後才有的機制，KIT-001 建立於其前。
追溯適用新格式會產生一份憑空編造的審查紀錄——那正是 `design_note.md` §2
第 2 類人工介入（宣稱 ≠ 實際）。結案理由改記在本檔與該工單的 §7。

**為什麼 §5「建議執行順序」也一併標過期（工單沒要求）。**
它與 §3 是同一種過期清單。只標 §3 而留著一份「1. Draft PR 2. 負向對照 …」的
編號待辦，下一個讀的人照樣會照它辦事。改成落點對照表，順便讓九項的完成度一眼可見。

**為什麼檔頭與 AC-03 是「改寫」而不是「追加」。**
`team_protocol.md` §1.8：要找出導致缺陷的那條敘述**直接改寫正確**，不可只在後面追加。
留著舊句子，下一個讀的人仍會照舊句子辦事——追加只是把矛盾留在檔案裡。

**為什麼三條互斥做法寫在 BACKLOG 而不是新開 DN。**
020 是清帳單，職責是「把卡點寫對」。開 DN 是探索工作，要有人推，混進清帳單會讓
兩件事都做不完整。冰箱那列現在的狀態是「待開 DN」，卡點與三條路都寫清楚了，
下一輪開 DN 的人不必重新推導。

## 5. 已知落差（不在本單處理）

- **冰箱區的改動 precheck 偵測不到。** `extract_existing_icebox()` 把手寫區原樣複製進
  重生的 BACKLOG，所以「BACKLOG 是否為最新」對這一區結構性失效。這不是缺陷是必然——
  手寫區沒有真值來源可比對。已在 `PEV-DEV-AGENT-022` §5 明文列為範圍外。
- **`Closed` 的時間格式不一致。** `PEV-DEV-AGENT-001` 是 `2026-08-16`（純日期），
  其餘都是帶時區的完整 ISO。precheck 的時間戳檢查**刻意接受**純日期並降到日期粒度比較，
  所以不會叫。要不要統一格式沒有結論，本單不動已結案工單（§1.11）。
- **補結案舊帳，在 BACKLOG 上幾乎無痕。** KIT-001 的 `Closed` 是 `2026-08-16`，早於
  「近期結案」前十名的時間門檻，結案後**直接進了「另有 11 張已歸檔工單未顯示」**。
  肉眼可見的變化只有：工單總數 22 → 24（含新開的 `021`／`022`）、歸檔數 9 → 11、
  「審查中」小計 1 → 0、kit_sync 統計由 In Review 轉 Done。
  這是「補的是帳不是工作」的必然結果——把 `Closed` 填成清帳當天它才會浮上來，
  但那是偽造。這一點值得記著：**BACKLOG 的「近期結案」是時間視窗，不是完成清單。**
- **`design_note.md` 仍有 328 行。** 轉成歷史索引後它的價值是 §1／§2 的診斷資料
  （4.7 MB／689 張工單的實測），那部分不過期。沒有折併或刪除的必要。
