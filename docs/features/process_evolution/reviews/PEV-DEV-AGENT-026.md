## 4. AC-04：失敗訊息的可行動性

三種失敗形態的訊息各自帶齊了「哪一份 skill、哪一行、期望什麼」：

| 形態 | 訊息 | 指名了 |
|---|---|---|
| 漏引用 | `qa-test-planner/SKILL.md 沒有引用 §1.12（該節標了「適用全角色」）` | 檔案、缺哪一節、為什麼該引用 |
| 編號不存在 | `backend-developer/SKILL.md:10 引用了不存在的 §9.9` | 檔案、行號、壞掉的編號 |
| 標題對不上 | `backend-developer/SKILL.md:26 §1.12 的標題對不上：期望「文檔權威階序」，實際「取證通道保真 做開工自檢。該」` | 檔案、行號、期望值、實際值 |

第三種特意把**實際文字**一起印出來，因為重編號情境下光看期望值無法判斷是
「skill 寫錯」還是「規範動了」——兩邊都印出來才看得出是規範位移。

## 7. 設計上的取捨與已知限制

### 7.1 標題比對用「反向」而非「解析」

原文的標題結尾沒有固定分隔符——現況同時存在 `）`、`。`、`、`、
` 的「模組前綴對照表」` 四種收尾。若先解析出「引用裡的標題」再去比對，
等於要窮舉所有收尾形態，改一次文案就可能誤報。

實作反過來：**取 `team_protocol.md` 的真實標題，斷言 `§X.Y ` 後面以它開頭**。
不需要知道標題在哪結束，而重編號情境下仍然正確轉紅（負向 3 已證）。

### 7.2 歸屬用「往前找最近的檔名」

`§1.9 程式碼隔離與分支、§1.10 Commit 閘門` 這種寫法只在第一個編號前寫了檔名，
第二個編號必須繼承。同一機制順帶讓 `git_workflow.md` §6.2／§8.3 正確落在
檢查範圍外（普查顯示剛好 2 筆，與人工盤點一致）。

### 7.3 檢查 B 的已知限制（AC-05）

已寫入 docstring：它依賴**規範作者記得寫「適用全角色」那四個字**。
沒標記的章節抓不到，因此它防的是「規範標了但 skill 沒跟上」，
**不是**「規範作者忘了標記適用範圍」。後者沒有機器判準——
一個章節該不該適用全角色是設計決定，不是可從文字推導的事實。

### 7.4 「已廢除的流程規則」表不加列

本工單沒有推翻任何既有流程規範，只是新增檢查。CLAUDE.md 要求的加列時機是
「推翻既有流程規範時」，不適用。
