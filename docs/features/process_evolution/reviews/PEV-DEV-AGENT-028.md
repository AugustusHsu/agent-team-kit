### 2.1 AC-03：沒有一條規則是憑空立的

七條規則的案例全部來自 `023`／`025`／`027` 或 DN-004 的實跑紀錄，
沒有「一般而言比較好」這種寫法。工單原文的要求是「寫不出案例的規則不收」，
執行時據此砍掉了兩個候選：「章節排序統一」與「檔頭要寫適用時機」——
兩者都有道理，但翻遍三張工單找不到因為沒有它而出過的錯，於是不收。

### 2.2 AC-04：跟 `team_protocol.md` 的分界

分界是**「怎麼寫」對「是什麼」**：

- 守則寫「進入主線前要取得同意」——**規則本身**。
- 本標準寫「引用這條規則時，檔名、編號、標題三者齊全」——**引用它的寫法**。

所以標準通篇沒有複述任何一條流程規則的內容，只寫格式、覆蓋範圍與篇幅。
第 3 節的分層表是唯一接近邊界的地方：它規定「誰要引用 §1.10」，
但那是覆蓋範圍不是規則內容，守則自己沒有、也不該有這張表。

### 2.3 兩個裁定（使用者 2026-08-22）

**必備章節分層**：§1.10／§1.11／§1.12 全員 13 份，§1.5／§1.9 只到施工側 6 份。
理由寫進標準第 3 節——判準是**「有產出就會 commit」**，
上游側的 BRD／PRD／HLD／wireframe 一樣要進 commit，所以「它們不需要 §1.10」不成立；
而分支操作與狀態機轉移只有實際跑流程的角色會做。

**篇幅 150 行軟上限**：實測 13 份呈雙峰（9 份 38～71 行、另一端 142～255 行），
150 落在兩峰之間，標記到 3 份。超過要在檔頭寫理由，不是禁令。

### 3.1 新照出來的一筆：`frontend-developer/SKILL.md:37`

正文寫著「**核心技術**：優先使用 HTML / React 結構搭配 **Vanilla CSS**」。
這是指令性句子，裝進 Vue／Svelte 專案就是**直接的錯誤指令**，
性質與 `027` 移除的「不可自行引入其他框架」完全相同。

**`025`～`027` 三輪盤點都沒抓到它。** 原因推測是當時的注意力集中在
`qa-automation-engineer` 那句明文禁令上——一句寫成「優先使用」的建議，
讀起來比「不可」溫和，但對 agent 的效果一樣是選型指令。
這一筆是本標準的第一個實證價值：**規則能指出現況哪裡不對，才不是在描述現況。**

依 AC-05「本張不修」，列進標準第 8 節並收進 `PEV-DEV-AGENT-033` §2.2。

### 3.2 界線：`description` 與舉例句不算違規

初掃命中 6 份具名框架，逐筆看過之後分成三類，只有一類是違規：

| 類別 | 例子 | 判定 |
|---|---|---|
| frontmatter `description` 的觸發關鍵字 | `qa-automation-engineer:3` 列出 Pytest／Jest／Playwright… | **不算**——列得越全召回越準，與規定專案用什麼無關 |
| 舉例句 | `backend-developer:33`「例如一小段 python 測試檔、`pytest` 建議或一組 `curl` 指令」 | **不算**——句型是「例如」，不會擋掉選型 |
| 指令性句子 | `frontend-developer:37`「優先使用 HTML / React」 | **算**（§3.1） |

這個界線在盤點時才浮現，於是回頭補進標準第 4 節——否則規則會被過度套用，
下一個人會去刪 `description` 裡的框架名，反而讓 skill 觸發不到。
