## 4. 過程中修正的一個做法錯誤（值得記下來）

**一開始我手改了兩份 README。** 根目錄 `docs/` 是 `./install.sh .` 裝出來的
唯讀安裝實例，正確做法是**只改 `kit/`，再跑 `./install.sh . --upgrade` 讓它傳播**。

我原本以為手改兩邊會在 dry-run 出現「待合併」。**實測推翻**——手改兩邊時
dry-run 回「新增 0、更新 0、已是最新 60、保留 4、**待合併 0**」，因為安裝器
判「已是最新」比的是內容是否等同 `kit/`，不是 manifest 基準線。

但它留下了一個安靜的後果，這才是走安裝器的真正理由：

| | `.agent/.kit-manifest` 的基準線 | 兩份 README 實際雜湊 |
|---|---|---|
| 手改兩邊後 | `9b09847e…`（**舊的**） | `93b13fcf…` |
| 走 `install.sh --upgrade` 後 | `93b13fcf…` | `93b13fcf…` |

歪掉的基準線當下不會報錯，要等到**下一次升級剛好動到這個檔**，安裝器才會把它
判成「本機修改過」而丟出假衝突 `.new`。走安裝器的路線因此多改了一個檔
（`.agent/.kit-manifest`），那正是手改路線會漏掉的那一個。

實際執行紀錄：`更新 1、已是最新 59、保留 4、待合併 0`。

## 5. 順手修掉的第二個缺陷：`\+` 在 BSD sed 不匹配

工單原本的候選寫法是 `sed 's/.*DN-\([0-9]\+\)_.*/\1/'`。`\+` 是 **GNU 擴充**，
BSD sed（macOS 預設）不認得，這是**出貨內容**，會直接落到別人的專案裡。

用 GNU sed 的 `--posix` 取近似證據（POSIX 語意即 BSD sed 遵循的那套）：

| 寫法 | 一般模式 | `sed --posix` |
|---|---|---|
| `\([0-9]\+\)` | `008` | `docs/design_notes/DN-008_review_panel_and_context_isolation.md` ❌ |
| `\([0-9][0-9]*\)` | `008` | `008` ✅ |

失效方式是**不報錯、原樣吐出整條路徑**。已改為 `[0-9][0-9]*`（POSIX BRE，
GNU／BSD 皆可），並在 README 加註「別『簡化』回 `\+`」——這種寫法看起來冗贅，
沒寫下理由的話下一個人幾乎一定會改回去。

可攜寫法實測取出全部 8 份編號：`001 002 003 004 005 006 007 008`，無遺漏。
