## 1. 背景：問題不是文檔大，是一個檔案裝了四種壽命

診斷來自 `../my_workstation`（本套件的第一個使用者專案）的實測數據：

| 指標 | 數值 |
|---|---|
| `docs/` 總量 | 4.7 MB、740 個 `.md`、58,289 行 |
| 工單總數 | 689 張（661 `Done`），其中 `-FIX-` 佔 **139 張（20%）** |
| 審查結論 | 232 次：187 `APPROVED`、45 `CHANGES REQUESTED`（**退回率 19.4%**） |
| 多輪工單 | 14 張進到第二輪，21 張出現第三輪 |
| 極端案例 | `LVS-DEV-EPIC-005.md` **107 KB**；`LVS-DEV-FE-FIX-033.md` **60 KB / 14 輪** |

**根因**：工單檔案同時承載四種產出物，而它們壽命完全不同：

| 內容 | 讀者 | 壽命 | 過期後果 |
|---|---|---|---|
| 描述 + AC（規格） | AI 執行時 | 到該工單 `Done` | **做錯東西** |
| Code Review 備註（逐輪堆疊） | 當下的人 + 要修的 AI | 到那一輪修完 | 無（純歷史） |
| HITL 問答 | 當下的人 | 到回答完 | 無（純歷史） |
| 決策理由 | 未來的人／AI | 專案生命週期 | 重蹈覆轍 |

兩種**壽命最短**的（審查紀錄、HITL 問答）佔掉大半體積。`FIX-033` 內文自承
「原始描述中的行號與部分假設**已過時**」——**檔案自己承認它在說謊**，
所以人不再閱讀它是理性反應，不是紀律問題。

## 2. 四類人工介入（分析用的主軸）

不要問「流程怎麼改」，要問**「每次被卡住，是哪一類卡住」**。
三類不夠——實測後必須拆成四類，第 2 類是原本漏掉且最貴的：

| # | 類別 | 實證案例 | 該怎麼處理 |
|---|---|---|---|
| 1 | **機械可判定** | `FIX-033` 第一輪退回主因就是 `npm run lint` **exit 1**（1 error／310 warnings）；另有未使用的 import | **CI 閘門。人與 AI 都不該看到** |
| 2 | **宣稱 ≠ 實際** ⭐ | 「AC-6 勾了但從未執行」（`ls .git/hooks/` 根本沒有 hook）；「偽綠燈測試」（5 個 mock 全是死碼、唯一斷言恆為 null） | **負向對照自動化**（見 §3.2） |
| 3 | **要判斷，但不必是你** | `retry()` 未清退避計時器造成重複寫入競態；AC-08 回滾對使用者不可見、錯誤提示鏈路整條斷開 | AI 審，結論進 PR，人只看摘要 |
| 4 | **只有你能決定** | 「建議二擇一，由使用者裁定 **(A) 於本工單補完 / (B) 拆出新工單**」 | 保留，但**批次化到 PR 閘門** |

### 第 2 類為什麼是主力

code-reviewer 自己在工單裡留下的紀錄（EPIC 第四次方法論驗證）：

> 「本輪三張工單的交付回報**全部宣稱 AC 達成**，若照單全收則 3/3 APPROVED。
> 實際以**負向對照**逐條驗證後，一張測試零鑑別力、一項 AC 從未執行、
> 一條『單軌制』在備援路徑失效——三項全部是『文字宣稱』與『實際行為』的落差，
> **且三項都無法從閱讀 diff 看出來，只能靠執行**。」

以及第六次：「**執行結果對了，不代表你對它的描述也對**。」

根因寫在 `FIX-033` 第二輪的自我揭露裡：

> 「⚠️ **利益衝突揭露**：本輪受審程式碼由本 AI 於同一 session 內撰寫，
> 屬**自我審查，獨立性不足**。」

**寫碼與審查同一個 context，agent 會相信自己的交付回報。**

### 還有一種「不是判斷」的純開銷

`FIX-033` **第三輪明文寫著「未再新增任何程式碼變更」**——整輪在做的是：
AC-08 的 `[x]` 改回 `[ ]`、§3.2 案例 7 加刪除線、Minor 移轉到 `FIX-042`、
Epic 子工單 N 值 37 → 38。**純記帳**。這是「工單檔案兼任資料庫」的直接代價。

## 3. 候選改進項

> 排序依投報率。每項的「待決」是畢業成工單前必須先回答的問題。

### 3.1 Draft PR + CI 閘門 ⬅ 最優先

**做什麼**：`In Progress` 一開始就開 Draft PR，CI 從第一個 commit 就跑
（lint / typecheck / test）。目標是消滅第 1 類——機械性失敗在人看到之前就已經紅了。

**狀態機對映**（PR 狀態取代「AI 寫進 md 的字串」，可查證、不漂移）：

| 工單 Status | PR 狀態 |
|---|---|
| `Ready` | （無 PR） |
| `In Progress` | **Draft PR**，CI 持續跑 |
| `In Review` | 取消 Draft，requested review |
| `In Progress`（退回） | PR 轉回 Draft |
| `Done` | **PR merged** |

**關鍵決定**：**`Done` = merged，不是 `APPROVED`。** 這樣 `git log main` 就是完成清單，
BACKLOG 可從 merged PR 生成，狀態漂移消失。

**分支命名**：`feat/PEV-DEV-BE-001-短描述`。純工單號在 `git branch` 列表不可讀；
加前綴讓自動化能分流（docs-only 的 PR 可跳過前端測試）。GitHub 與 GitLab
都會自動偵測分支名裡的工單 ID 並建立關聯。

**待決**：
- CI 要跑哪些檢查？本 repo 目前只有 `uv run pytest`，需要補什麼？
- 廠商中立怎麼落實？狀態機與閘門完全中立；語彙統一用「合併請求」；
  指令抽成薄 adapter（`gh pr create --draft` ↔ `glab mr create --draft`，近乎一對一）。
  adapter 放哪、要不要做成 shell wrapper？

### 3.2 負向對照自動化

**做什麼**：新增的測試若在**還原目標 commit 後依然全綠**，代表零鑑別力，CI 直接擋下。
工程上的既有名字是 mutation testing／負向控制。

**為什麼不能省**：PR 解決的是「審查者換一個 context」，但**如果 CI 只跑既有測試、
而測試本身是偽綠燈，PR 一樣會放行**。它與 §3.1 互補，不是替代。

**待決**：
- 全量 mutation testing 太慢，要不要只對「本次 PR 新增的測試」跑負向對照？
- 怎麼自動決定「還原到哪個 commit」？
- 做成 kit 出貨的通用腳本，還是各專案自己實作？

### 3.3 審查與開發拆成不同 context

**做什麼**：靠 PR 天然達成——reviewer 從 PR diff 開始，不繼承開發 session 的記憶。

**待決**：光靠「不同 session」夠不夠？要不要在 `code-reviewer/SKILL.md` 明文
禁止採信交付回報的宣稱、一律回查程式碼？

### 3.4 審查清單三分法（precheck 腳本）

**做什麼**：`code-reviewer/SKILL.md` §1 的四維度裡，有一大票是機械可判定的，
不該消耗 AI 判斷力，也不該有非決定性：

| 現行判準 | 位置 | 該歸誰 |
|---|---|---|
| 殘留 `console.log` / `print` / `// TODO` | C 維度 | grep |
| `dangerouslySetInnerHTML` / `eval` / 未擋 `javascript:` href | B 維度前端③ | grep |
| Hard-coded secrets | B 維度 | 正則 |
| 有沒有寫對應測試 | D 維度 | 檔案存在性 |
| 交付回報缺「🔒 資安自查」段落 | B 維度 | 字串檢查 |
| **AC 是否 100% 滿足、有無過度設計** | A 維度 | **AI** |
| **依角色隱藏 UI 時後端是否也有授權檢查／IDOR** | B 維度④ | **AI** |

**待決**：
- kit 要裝進任何專案，pattern 必須可設定（純後端專案沒有前端那組），設定檔放哪？
- 維持 stdlib-only（配合 CI 的 `stdlib-only` job）？
- 新增腳本要同步登記 `kit/docs/DOCS_MAP.md`。

### 3.5 工單瘦身：審查紀錄與 HITL 移出

**做什麼**：工單只留描述、AC、**濃縮過的**決策理由、PR 連結。
審查輪次與 HITL 問答移到 PR 留言（分執行緒、有時間戳、可 resolve、可摺疊）。

**注意**：`team_protocol.md` §1.8「找出導致缺陷的那條 AC 直接改寫」**應保留**——
實測顯示 AC 區是健康的，撐爆檔案的是審查紀錄，不是 AC。

**待決**：PR 平台若日後更換，留言會不會失聯？要不要在工單留摘要 + 連結？

### 3.6 worktree 重新設計

**現況**：`kit/docs/standards/worktree_workflow.md` **20 KB，是整個 kit 最大的文件**，
其中 §6 防孤兒機制、§5.2 `git branch -d` 誤報陷阱、§5.3 force 代價分類佔大半。

**實證**：本 repo 於 2026-08-16 清理時，實際存在 **2 個孤兒 worktree**
（其中一個帶著未合併的 commit）。**四層防孤兒機制沒有守住。**
詳見已取消的 `WTG-DEV-BE-001`。

**重新設計的關鍵前提**：**worktree 的價值是「同時擁有多個工作目錄」，不是「隔離」——
隔離是 branch 給的。** 導入 PR 後分支會 push 到 remote，worktree 目錄砍掉也不丟東西，
防孤兒機制的必要性蒸發九成。

**判準**：會不會同時需要兩個目錄各自跑起來（兩個 dev server、兩套 compose）？
會 → 用；不會 → 只開 branch，`git switch` 足夠。

**目標**：20 KB → 約 3 KB，只留「何時值得開／開幾個／怎麼收」。
§5.1 的 `--ff-only` merge 流程可整段刪除（merge 改由 PR 執行）。

**待決**：本專案已停用，那 kit 出貨版要保留到什麼程度？

### 3.7 Discord 作為通知與批准層

**定位**：**通知／批准層，不是文檔層。** 只推第 4 類（只有人能決定的）給使用者，
讓批准可以在手機上完成，而不必坐回電腦開一個大檔案。

**待決**：等 §3.1～§3.5 落地、輪數降下來再評估。現在接通知只會得到一個會震動的瓶頸。

### 3.8 展示層（人類可讀的高抽象視圖）

**命名**：要的是**展示系統**，關鍵字是**「生成」不是「維護」**。

**鐵則**：**展示層 100% 從 source of truth 生成，零手工維護。改展示層 = 改生成器。**
依據是本專案自己的教訓——`5f844242` 的 commit 訊息記載
`docs/standards/team_protocol.md` 的拷貝「**已與正版分岔 53 行、缺 §1.7/§1.8**」。
**任何需要手動維護的第二份表述，必然漂移。**

| 要展示的 | 資料來源 | 做法 |
|---|---|---|
| 工單看板／進度 | 工單 metadata + merged PR | 擴充 `scan_backlog.py` |
| 後端流程圖 | **Mermaid，寫在 `.md` 裡** | GitHub/GitLab 原生渲染 |
| 架構關聯 | 各模組 hld/lld 的 Mermaid 區塊 | 同上 |
| 前端展示 | 既有 wireframes | 靜態站台 |

**Mermaid 是關鍵**：同時滿足「AI 可 grep 的純文字」與「人類看得到的圖」，
且不需要任何額外系統。站台本體用 MkDocs Material 或 Docusaurus 從 `docs/` 建置，
**deploy 到 GitHub Pages 而不是塞進專案頁面**。

**排序理由**：這項**排最後**。現在的 docs 生不出好看的展示，因為工單裡混著四種壽命的
內容，生成器不知道該抽哪一段。先做 §3.5，展示層會變成很小的工作量。

### 3.9 design_note 本身的落點與範本 ⬅ 元問題

**現況**：本文件就是第一份 design note，但**放在哪、長什麼樣都還沒定義**，
目前的位置（`docs/features/{模組}/design_note.md`）是暫定。

**暫定落點的理由**：`_TEMPLATE/` 已有模組層級文件（`prd.md`／`hld.md`／`lld.md`／
`api_spec.md`／`test_plan.md`）。design note 就是**再前一階段**的模組層級文件——
在 PRD 之前的探索期產物。所以自然的家就是模組目錄。

**待決**：
- 確認落點：`docs/features/{模組}/design_note.md`？還是 `design_notes/DN-0XX_*.md` 支援多份？
- **範本要有哪些欄位**？至少：狀態、建立日、觸發原因、待決事項、畢業條件
- **生命週期**：什麼時候該畢業成工單？畢業後 design note 保留還是折併進 `prd.md`／`hld.md`？
  （對照 `documentation_conventions.md` §2.1 補充檔「工單 `Done` 後折併回主文件」的既有規則）
- **與 Icebox 的關係**（本次已定調，要寫進規範）：
  **Icebox 放一行索引，design note 放實質內容，兩者一對一。**
- 要不要納入 `_TEMPLATE/`、登記進 `DOCS_MAP.md`？
- 要不要在 `documentation_conventions.md` 增設一節？

## 4. 已定調的原則（不需再討論）

1. **Notion AI 不導入。** 主要讀者是 AI（靠 grep），搬進 Notion 要付 MCP round-trip；
   且會切斷「程式碼與文檔同一個 commit」這個唯一防漂移機制；而且不解決問題——
   107 KB 的工單搬過去還是 107 KB。
2. **Discord 只做通知／批准，不做文檔。**
3. **headroom 留著，但別指望。** 它壓縮的是飛行中的 context，不是 source of truth。
   ⚠️ 副作用待查：它會壓縮工具輸出，**code-reviewer 讀 diff 時可能讀到壓縮版**，
   審查場景下是風險。
4. **工單留在版控。** 上游文章主張「實作計畫書不進版控」，該建議**只適用於審查輪次與
   HITL 對話**，不適用於工單本身——工單是本套件的核心。
5. **收斂＝直接做（一次性）；改進＝走工單（持續）。** 理由是 bootstrap 悖論：
   不能用還沒安裝的流程來安裝流程。
