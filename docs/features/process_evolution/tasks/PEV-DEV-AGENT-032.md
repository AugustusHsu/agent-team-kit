## 1. 任務描述 (Description)

`kit/docs/standards/git_workflow.md` §7「並行擴充」目前**整節是空的**，原文寫著
「多張工單同時進行時的工單拆分與分支拓撲規則，尚在 DN-005／DN-006 探索中，
**定案後補入本節**」。本工單就是補那一節。

**觸發事件**：2026-08-19 把 `030`／`029`／`025` 三張工單以堆疊分支、三次 `--no-ff`
併回整合分支，`git log --graph` 長出階梯狀圖形。使用者質疑後查證發現——
**規範沒有被違反，是規範根本沒管這件事**。上一輪是把單線規則硬套到三張工單上。

**規範依據是使用者裁定，不是 DN。** [DN-006](../../../design_notes/DN-006_branch_topology_and_isolation.md)
仍是 `🔍 Exploring`，依 `team_protocol.md` §1.11 **不在文檔權威階序內**，
不能當實作依據。本工單引用 DN-006 §3.4 只是取用它的**沙盒實測數據**。

## 2. 規格：輸入與輸出 (Inputs & Outputs)

### 2.1 ⚠️ 開工後修訂：形狀由 C 改為 E

**本工單建立時寫的是形狀 C（一條 round 分支帶多張工單）。開工讀規範時發現兩個
建單時漏掉的連動點，而且都是硬衝突：**

| 漏掉的連動點 | 為什麼是硬衝突 |
|---|---|
| `git_workflow.md` §1 核心原則 1「**一張工單 = 一個分支，分支名 = Task ID**」 | §1 開頭明文「以下三條**不可協商**」。形狀 C 直接違反 |
| `kit/.agent/resources/team_protocol.md:129` 同一條原則 | 那是**適用全角色的正版協作守則**，比 git_workflow.md 更上游 |

順帶還有 §2 粒度表「分支 : 工單 = **1 : 1**」、§3「分支名 = Task ID」。

**形狀 E 讓這些全部不必動。** 做法：三張工單**各自**開分支（原則 1 不變），
依內容依賴堆疊，**只把最上層那條 merge 回整合分支**。

沙盒實測（`$CLAUDE_JOB_DIR/tmp/topo/buildE.sh`）證實兩件事：

1. **圖形與形狀 C 完全相同**——一顆 merge commit、三顆側支 commit、`|/` 收線。
2. **`git branch -d` 逐張仍然成功**（T030／T029／T025 三條全成功）。
   原因：下層 commit 是上層的祖先，最上層一合併，三條同時成為主線祖先。

第 2 點使**使用者原本裁定的「`Done` 訊號拆解」變得不需要**——§6.4 一個字都不用改，
逐張刪除、逐張確認的能力原封不動。使用者 2026-08-19 確認改採形狀 E。

### 2.2 已裁定的形狀

**一輪多張工單：各自開分支 → 依內容依賴堆疊 → 只 merge 最上層那條。**
中途不合併任何一條回整合分支。

### 2.3 本工單要回答的設計問題

| # | 問題 | 現況 |
|---|---|---|
| A | 合併訊息第一行的 Task ID 怎麼寫 | **仍要答**。§6.1 要求第一行含 Task ID，三張工單的完整 ID 一行放不下 |
| B | 輪次分支怎麼命名 | **已消失**。形狀 E 沒有輪次分支，每條都是 `{TaskID}` 分支 |
| C | 單線與多工單的分界寫在哪一節 | **仍要答**，但範圍縮小到「主線讀法」一項 |

**A 的實測依據**（`$CLAUDE_JOB_DIR/tmp/topo/msgprobe.sh`）：第一行用共用前綴縮寫
（`[PEV-DEV-AGENT-030／029／025]`）、Body 逐條列完整 ID 時——

| 查詢方式 | 結果 |
|---|---|
| `git log --oneline --first-parent` | ✅ 看得出這輪有哪些工單 |
| `git log --grep=PEV-DEV-AGENT-029` | ✅ 用完整 ID 反查得到那顆 merge commit |
| `git log --oneline \| grep PEV-DEV-AGENT-029` | ❌ **找不到**——第一行是縮寫 |

第三列是規範必須寫明的坑：**反查要用 `--grep`，不是 `--oneline | grep`。**

**C 的設計約束**：§7 現有的 📌 註記已定調「規則只有一套……**多人開發包含單人開發**，
單線專案讀基本節就完整可用」。基本節的敘述要改成不預設單線的中性寫法，
**不得**讓單線讀者為了看懂基本節而被迫讀 §7。
