## 1. 任務描述 (Description)

`kit/docs/standards/git_workflow.md` §7「並行擴充」目前**整節是空的**，原文寫著
「多張工單同時進行時的工單拆分與分支拓撲規則，尚在 DN-005／DN-006 探索中，
**定案後補入本節**」。本工單就是補那一節。

**觸發事件**：2026-08-19 把 `030`／`029`／`025` 三張工單以堆疊分支、三次 `--no-ff`
併回整合分支，`git log --graph` 長出階梯狀圖形。使用者質疑後查證發現——
**規範沒有被違反，是規範根本沒管這件事**。上一輪是把單線規則（一分支一工單）
硬套到三張工單上，才長出那個形狀。

**規範依據是使用者裁定，不是 DN。** [DN-006](../../../design_notes/DN-006_branch_topology_and_isolation.md)
仍是 `🔍 Exploring`，依 `team_protocol.md` §1.11 **不在文檔權威階序內**，
不能當實作依據。本工單引用 DN-006 §3.4 只是取用它的**沙盒實測數據**；
規範來源是使用者 2026-08-19 的兩次裁定。

## 2. 規格：輸入與輸出 (Inputs & Outputs)

**輸入：** 使用者 2026-08-19 裁定（§2.1）、DN-006 §3.4 的四形狀實測數據。

### 2.1 已裁定、不得再議的兩件事

| # | 裁定 |
|---|---|
| 1 | **一輪多張工單走一條分支，主線只有一顆 merge commit。** 側支保留各工單自己的 commit（形狀 C） |
| 2 | **`Done` 訊號拆解**：`git branch -d` 成功只證明「**輪次已合併**」；工單是否完成改由合併前**逐張確認 AC 與審查檔** |

裁定 2 之所以成立，是因為審查檔 `docs/features/<模組>/reviews/<TaskID>.md`
**本來就一張工單一份**，不隨拓撲改變——逐張確認的載體一直都在，
以前只是借用了 `branch -d` 這個順手的訊號，把兩件事綁成一件。

### 2.2 本工單必須自己回答的三個設計問題

裁定只定了形狀與訊號，下面三項還沒有答案，**逐條都要在 §7 裡有明文**：

| # | 問題 | 為什麼躲不掉 |
|---|---|---|
| A | 合併訊息第一行的 Task ID 怎麼寫 | §6.1 硬性要求「合併 commit 的訊息第一行必須含 Task ID」，形如 `<類型>: [{TaskID}] <主旨>`。三張工單共用一顆 merge 時這條要怎麼滿足 |
| B | 輪次分支怎麼命名 | §3.1 現在寫死「分支名就是 Task ID」 |
| C | 單線與多工單輪次的分界寫在哪一節 | §7 是「並行擴充」，但裁定會動到 §6.1／§6.4／§4 這些**基本節**的文字 |

> 📌 **B 比看起來簡單，別在這裡耗時間。** §6.1 已經寫明
> 「**分支名不會自動進入 commit 物件**——自訂合併訊息會蓋掉 git 預設的
> `Merge branch '{TaskID}'`」。也就是說**分支名根本不進歷史**，
> 追溯完全靠合併訊息裡的 Task ID（問題 A）。B 因此只是人體工學問題，
> 不影響任何可追溯性，挑一個一致的寫法即可。

**C 的設計約束**：§7 現有的 📌 註記已定調「規則只有一套……**多人開發包含單人開發**，
單線專案讀基本節就完整可用」。所以基本節的敘述要改成**不預設「一分支一工單」**的
中性寫法，具體的多工單規則放 §7——**不得**讓單線讀者為了看懂基本節而被迫讀 §7。

本次的性質需要實作者親自判斷：多數改動是**加但書**（單線仍然一張工單一行），

傾向要加一列。**判斷結果與理由都要寫進審查紀錄**——結論是「不加」也可以，
但必須寫出為什麼不加。
