## 1. 任務描述 (Description)

冰箱裡「審查與開發拆 context」的判準是：**只有一種做法就開工單，有多種就開 DN**。
實查後確認這一項裡面**兩種都有**，使用者 2026-08-17 裁定拆兩半：

| 部分 | 做法數 | 去向 |
|---|---|---|
| 審查者的**取證義務**（不得採信宣稱、一律回查） | 一種，AC 當場寫得出來 | **本工單** |
| context **隔離機制**（同 session／subagent／獨立 session／換模型） | 至少四種，成本差很大 | 併入 [DN-004](../../../design_notes/DN-004_skill_system_realignment.md) |

**現況的缺口是實查出來的**：`code-reviewer/SKILL.md` 全長 113 行，
只有第 95 行規定「不代為 commit／合併」，**沒有任何一條說審查結論要有證據**。
而 §0 反倒明文要求「讀取開發者的交付回報」——在同一個 session 裡開發完自己審自己時，
「回報」根本不是外部輸入，是自己剛寫的字。這條路徑上，審查可以完全不看程式碼就通過。

`team_protocol.md` §2.2 定義了三段式交付回報的格式，§2.3 定義審查後的回寫，
但**兩者都沒說審查結論的證據該從哪來**。這就是本工單要補的洞。

## 2. 規格：輸入與輸出 (Inputs & Outputs)

**（a）正版規則**——`team_protocol.md` §2.3 新增條款：

- 交付回報是**線索，不是證據**。每條 AC 的通過與否，必須回到程式碼、diff、
  或實際跑出來的輸出來判定；「回報說已完成」不構成通過。
- 審查報告必須附**客觀指標**：可重跑的指令與其輸出（測試數、`grep -c` 計數、
  升級摘要的待合併數等），讓第三者不必信任審查者本人也能複核。
- 本次若新增測試，需附**負向對照**結果（把修正還原，確認新測試確實會紅）。
  自動化這件事仍在冰箱（要跑在 CI 上），但**手動做並附結果**現在就要求。
- 無法客觀驗證的 AC，明說「僅人工判讀」，**不得偽裝成已驗證**。

**（b）skill 落地**——`code-reviewer/SKILL.md` §0 補上取證義務，
§4 的報告格式新增必填段落「📊 客觀指標」。

**（c）DN-004**——新增一節，把 context 隔離的四種機制與各自成本列為待決，
並註明取證義務已由本工單處理，DN 不必再涵蓋。

**（d）冰箱**——「審查與開發拆 context」列移除（已決定去向）。

### 僅人工判讀的部分

- 「規則寫下去之後，審查者是否真的會照做」**無法客觀驗證**。本工單只能保證條款存在、
  位置正確、且被 skill 引用；行為面的驗證要等 DN-004 的 context 隔離機制定案，
  或等冰箱裡「負向對照自動化」落到 CI 上。
- DN-004 §5 的四種機制成本欄位是**判斷**而非量測（例如「subagent 的回報難以查核」），
  刻意留在 DN 而不寫進規範，就是因為還沒有證據等級的支撐。
