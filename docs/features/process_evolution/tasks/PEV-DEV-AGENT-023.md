## 1. 任務描述 (Description)

`PEV-DEV-AGENT-017`（Done）量出「工具輸出在進入 context 前會被中間層改寫」，
但它的結論只落成兩處**讀法紀律**：`code-reviewer/SKILL.md` §0 一條，
正版條款寄生在 `team_protocol.md` §2.3「Code Reviewer → Done／退回」的一個 bullet。
這留下兩個缺口：

**① 綁錯角色。** 正版掛在 §2.3 底下，位置本身就在說「這是審查者的事」。
但取證不是審查者專屬動作——開發者讀測試輸出、QA 讀失敗 log、DevOps 讀部署結果，
拿到的都是同一條可能被改寫的通道。**寫在交接規範裡的規則，其他角色沒有理由去讀。**

**② 只有被動規避，沒有主動自檢。** 現行規則是「看到異常就換讀法重讀」，
前提是**你認得出異常**。但 017 §2.1 實測最嚴重的那一種失效**完全不留提示**：
一列 Markdown 表格加前後各一句散文，散文整段消失、沒有 hash、沒有標記。
認不出來的東西，靠「看到就換讀法」是空的。

2026-08-18 的追查補上 017 沒有的根因層事實，兩點改變規範該怎麼寫：

- **這不是機率，是設定。** 中間層有明確的「工具保護名單」概念，預設保護檔案讀取類工具、
  **刻意不保護 shell**（其原始碼註解直言 shell 輸出是理想的壓縮目標）。
  017 §2.4 量到「檔案讀取工具乾淨、shell `cat` 被改寫」因此是設計必然而非運氣。
- **保真通常是可設定的，不是只能規避。** 該類中間層普遍提供把工具加進保護名單的開關。
  這正是第 2 層該填的東西——**kit 不知道使用者用哪一套，但可以規定專案必須把它寫下來。**

依 `DN-007` §3.2 的兩層拆分：**第 1 層（技術棧無關、kit 可定義）** 寫規範、自檢程序與判準；
**第 2 層（技術棧綁定）** 留 hook 給專案填自己的通道設定。
`017` AC 立的界線「出貨規範不得寫死特定工具名」在本工單繼續生效。

## 5. 範圍外 (Out of Scope)

- **不進 `precheck.py`。** 保真檢查的輸入**不在 repo 內**——它量的是 agent 執行環境的
  工具通道，不是檔案內容。CI runner 裡沒有 agent 的 context，shell 輸出必然保真，
  這項檢查會**永遠綠燈**。那是假閘門，與 `DN-007` §4.1 裁定 3 否決 pre-commit hook 的
  理由完全平行：「裝了卻被繞過的閘門比沒有更糟，因為它讓人以為已經檢查過了」。
  §1.12 因此把它定為**開工時的人／agent 自檢**，不是 CI 檢查項。
- **不改 `PEV-DEV-AGENT-017`** 及其審查檔（§1.11「不改它，也不引用它」）。
- **不寫特定中間層的設定方式**進出貨內容——那是第 2 層，由專案自己填。
