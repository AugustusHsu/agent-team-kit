## 1. 問題陳述

多 agent 讓「多人並行開發」第一次在單人專案裡真的可行。但 kit 的工單體系
**是為單線執行設計的**，把它直接拿去跑並行會缺三樣東西：

- **Epic → 子工單是分類關係，不是排程關係。** 現行 Epic 只表達「這些子工單同屬一件事」，
  沒有任何欄位說得出「這兩張可以同時做」或「這張要等那張」。並行的第一個前提就沒有載體。
- **依賴只在開單當下宣告一次。** 工單的 `Inputs`／依賴欄位是靜態的。
  但並行開發最常見的事故正是**執行到一半才發現新依賴**——這在現行模型裡無處可記。
- **沒有「契約」的概念。** 兩張工單能不能同時開工，取決於它們之間的介面穩不穩定，
  而不是它們屬不屬於同一個 Epic。kit 目前沒有任何地方在描述介面穩定度。

## 2. 四個要支援的場景

使用者提出的並行需求可以分成四類，難度遞增：

### 2.1 多 EPIC 並行

不同 Epic 各派一個 agent。這是最容易的一類——Epic 之間本來就假設低耦合。
主要風險是**熱點檔案**（見 DN-006 §4）。

### 2.2 單一 EPIC 內並行

同一個 Epic 底下的子工單同時開工。比 2.1 難，因為同 Epic 的子工單**通常共用介面**，
正是最容易撞在一起的組合。這一類需要 Epic 工單本身能表達依賴拓撲。

### 2.3 競爭式開發

同一個問題同時開多個分支做不同解法，跑完測試再選一個 merge，其餘丟棄。
使用者明確點名這是並行的優點之一。

已知的成本結構：**被丟棄的分支仍然吃掉一次完整審查**。所以這一類的邊界不是
「能不能做」，而是「什麼樣的題目值得做」——探索性、評判標準客觀可測（跑得過／跑不過、
快多少）的題目才划算；規格明確的實作題做競爭式是純浪費。

### 2.4 執行期發現需要改 spec／文檔 ⭐

使用者補充的重點，也是四類裡最難的一類。原話：

> 在某個開發中遇到需要修改 spec 或者文檔時需要優先處理這部份，在透過類似 rebase
> 或相同功能的方式來處理，然後另一個分支/agent 需要對這個改動做適應，譬如說開發前端
> 遇到需要後端增加支援新的功能或是相同層級的更改，導致對應的前端也需要做修改

拆開來是三個獨立的問題，現行流程**一個都答不出來**：

1. **發現的當下要怎麼辦？** agent 手上有一張前端工單，卻發現後端要先改。
   它應該就地把後端也改了（範圍蔓延）、停下來等（阻塞）、還是開一張新工單（誰來開、誰來核）？
2. **改完之後怎麼讓別人知道？** 已經在跑的其他分支／agent，它們的 context window
   看不到這件事。規範層面要有一個「傳播」動作，不能靠人記得去講。
3. **別人怎麼適應？** 誰負責解衝突、什麼時候解、解不掉時退回哪裡。

## 3. 業界做法盤點

### 3.1 契約先行（contract-first）

主流答案是**先議定介面契約，再各自實作**。前端不等後端，改成對著契約
（OpenAPI／型別定義）＋ mock 開發，兩邊同時進行。

代價是**漂移（drift）**：前端對著假想的 schema 開發，真 API 落地時才發現對不上，
於是多花一個 sprint 把不相容的東西接起來。壓制漂移的手段是把契約變成**可執行的檢查**
（生成型別、契約測試進 CI），而不是一份會過期的文件。

對 kit 的意義：這條把「什麼時候可以並行」從一個直覺問題變成一個**可判定**的問題——
**介面契約已落地 = 可以並行；還沒落地 = 不可以**。這比「同不同 Epic」精確得多。
參考：[API contracts: a frontend survival guide](https://evilmartians.com/chronicles/api-contracts-and-everything-i-wish-i-knew-a-frontend-survival-guide)、
[API-first in practice](https://dev.to/dmitrii-verbetchii/api-first-in-practice-how-we-made-frontend-types-predictable-and-stable-332c)

### 3.2 Parallel Change（expand / migrate / contract）

場景 2.4 的標準解法，Martin Fowler 命名的
[Parallel Change](https://www.martinfowler.com/bliki/ParallelChange.html)，
又叫 expand-contract。把一個破壞性介面變更拆成三個階段：

| 階段 | 動作 | 狀態 |
|---|---|---|
| **Expand** | 新版與舊版並存，**只加不刪** | 舊消費者完全不受影響 |
| **Migrate** | 消費者逐一從舊版搬到新版 | 新舊並存，各自可獨立進度 |
| **Contract** | 全部搬完後移除舊版 | 收斂 |

兩個不變式：**沒有東西依賴它之前，不移除；還不存在的東西，不強迫採用。**

關鍵性質是**每個階段都與前一階段相容**，所以系統的不同部分可以停在不同階段，
不需要同步發布。這正好是「另一個分支/agent 需要對這個改動做適應」的答案——
適應不必是即時的，可以排進那個分支自己的節奏。

**已知失敗模式：忘記 contract。** expand 和 migrate 做了、contract 沒做，
系統就永久留著兩套路徑，新人不知道哪套是現行的，之後每次改動都要顧兩邊。
業界的緩解方式是**在開 expand 的當下就排定 contract**——它們是同一個決定的兩半，
不是相隔數月的兩個決定。
參考：[Expand/Contract without a big bang](https://blog.thepete.net/blog/2023/12/05/expand/contract-making-a-breaking-change-without-a-big-bang/)、
[Thoughtworks Radar: API expand-contract](https://www.thoughtworks.com/radar/techniques/api-expand-contract)

### 3.3 ⚠️ AI agent 特有的陷阱

這條對 kit 特別重要，因為 kit 的執行者**就是** agent：

> 指揮 agent 做 parallel change 時，必須把三個階段當成**三個獨立任務**下達。
> agent 若一次收到「把 X 改名成 Y」，它會把定義和所有呼叫端改在同一個 diff 裡——
> 那正是你想避免的 big-bang 變更。

—— [Encyclopedia of Agentic Coding Patterns: Parallel Change](https://aipatternbook.com/parallel-change)

換句話說：**expand／migrate／contract 三階段在 kit 裡必須是三張工單**，
不能寄望寫在同一張工單的 AC 裡讓 agent 自己分階段。這是規範層要處理的事，不是提示詞技巧。

### 3.4 任務拆解與並行標記

- **[GitHub Spec Kit](https://github.com/github/spec-kit)**（MIT，約 111k stars）：
  `/speckit.tasks` 產出依賴排序的任務清單，可並行的標 `[P]`。
  但 `[P]` **只是建議標記**——它不管隔離、不管衝突、不管誰先 merge。
- **GSD**：波次（wave）執行，同波次內並行、波次之間有依賴閘門。
- **scaffold-then-split**：先由一個 agent（或人）把共用契約立起來並 merge 進主線，
  再分派實作 agent。契約還不穩定的部分，先交給人做一次短設計衝刺，不要丟給 agent 並行。

共同結論：**並行的前提是依賴拓撲先被算出來，而不是先開工再看誰撞誰。**

## 4. 已知的邊界條件

- **多人開發包含單人開發**（使用者明確要求）。因此規則**寫一套**，
  內部分「基本」與「並行擴充」兩節；不做單人版／多人版兩份規範。
  單線專案讀基本節就完整可用，並行擴充節對它是 no-op。
- **本檔的 `agent` 是能力需求，不是廠商名稱。** 拆解結果要說明每個節點需要的角色、
  隔離與工具能力；Claude Code、Codex 或未來供應商由 [DN-009](DN-009_multi_agent_capability_routing.md)
  在執行時依可用性選擇。本檔不建立「某類工單固定給某家」的第二套路由規則。
- **需要人判斷的部分要放大審查粒度**（使用者要求），以降低人工負擔。
  但審查粒度放大與競爭式開發（§2.3）的「每個被丟棄的分支仍吃掉一次審查」是**衝突的**，
  這組張力需要在 Exploring 階段解掉。
- **實務並行上限 2～5 個 agent**。超過後審查與合併成本會吃掉並行收益；
  多份指引建議從 2～3 起步。
- **語法合併成功 ≠ 語意一致。** [CodeCRDT](https://arxiv.org/pdf/2510.18893) 的實驗
  即使保證 100% 收斂、零 merge 失敗，仍觀察到 5～10% 的語意衝突。
  這代表**自動合併不能當成驗收**，並行的終點一定要有一次整合驗證。
- **本 repo 自己是單線的**，會是新規則的第一個使用者，但**不會是它的壓力測試場**。
  規則的並行擴充節在這裡驗不出來。

## 5. 選項、取捨與裁定

### 5.1 依賴拓撲的來源（使用者已裁定，2026-08-27）

| 方案 | 寫入工單的來源資料 | 問題 |
|---|---|---|
| A. 手寫 `[P]`／wave | 每張工單直接標可並行或第幾波 | 容易在新增依賴後過期，同一份資訊要人工維護兩次 |
| B. 只寫 `blocked-by` | 工單只記正向硬依賴，wave 與 `[P]` 由 DAG 推導 | 無法單獨說明共享契約與檔案所有權 |
| **C. 最小來源組合（建議）** | `Blocked By`＋`Write Scope`＋`Contract` | 欄位較多，但每欄回答不同問題，可機械計算且沒有正反向重複 |

建議 C 中，`Blocked By` 只存前置 Task ID，`blocks` 反向關係由掃描器算出；`Write Scope`
承接 DN-006 的輪次內動態所有權；`Contract` 指向第 1 層契約檔，無共享介面時填 `—`。
`[P]` 與 wave 都是**輸出視圖**，不得手抄回工單成為第二份來源。

### 5.2 可以並行的判準（使用者已裁定，2026-08-27）

| 方案 | 判準 | 失效方式 |
|---|---|---|
| A. 不同 Epic／模組 | 分類不同就並行 | 仍可能共用設定、路由、schema 等熱點 |
| B. 只看檔案是否重疊 | `Write Scope` 不交集就並行 | 不同檔案仍可能透過同一 API／資料契約語意耦合 |
| **C. 四項全中（建議）** | DAG 無先後、Write Scope 不重疊、共享契約已落地、外部副作用可隔離 | 開工前多一道計算，但把語法衝突與語意衝突一起納入 |

Epic／模組只作為低耦合提示，不是放行條件。共享契約「已落地」指契約檔已存在於該輪 base，
且負責建立它的前置工單已合併；只在另一個未合併分支裡不算穩定 base。

### 5.3 執行中發現新依賴（使用者已裁定，2026-08-27）

建議不新增 `Blocked` 狀態，沿用現行五狀態：原工單保持 `In Progress`，但受影響範圍立即停寫，
branch／worktree 原地保留。接著依範圍分流：

- 新工作仍屬原目標與 `Write Scope`，且不需另一位 owner：修正原工單 AC／Outputs 後繼續。
- 超出 `Write Scope`、需要另一角色，或會使原目的顯著膨脹：由 Scrum Master 開新的前置工單，
  回填原工單 `Blocked By`；前置完成前原工單維持暫停。
- 新方案仍寫不出可驗收 AC：依 DN-001 改開 DN，不硬開內容模糊的前置工單。
- 新前置會讓輪次超過 5 張或改變原目標：停止擴張，回到使用者重新規劃輪次。

其他活躍工單若引用同一 `Contract` 或其 `Write Scope` 受影響，也一併收到變更傳播；
沒有命中的工單可繼續，不因一處阻塞凍結整輪。

### 5.4 Parallel Change 的載體（使用者已裁定，2026-08-27）

| 方案 | 做法 | 取捨 |
|---|---|---|
| A. 新增三種 Task Type | `expand`／`migrate`／`contract` 各自成 queue | 把變更階段誤建成角色／佇列，路由語意被污染 |
| B. Epic 特例 | 只在 Epic 裡寫三階段 | 非 Epic 的破壞性變更無法套用 |
| **C. 普通工單＋Change Set（建議）** | 三張普通工單共用 Change Set，phase 分別為 expand／migrate／contract | 多兩個 metadata，但不改 Task Type 與 Assignee 語意 |

採 C 時，開 expand 的當下就同時建立 contract 工單；contract 的 `Blocked By` 列出所有 migrate
工單，所以一開始是 `Pending`，直到消費者全數遷移才會變 `Ready`。這把「記得日後清理」
變成依賴圖的一部分，而不是一句容易遺忘的備註。

### 5.5 競爭式開發的成本閘門（使用者已裁定，2026-08-27）

建議只在「方案互斥、優劣事前不確定、且客觀評判方式能在開工前凍結」時進場。
不同候選必須使用同一組測試／benchmark／eval，且不得產生不可逆外部副作用。
安全政策、資料 migration、合規或只能憑主觀喜好判斷的題目，不適用競爭式開發。

成本上限採結構限制，不綁特定 token 或天數：預設最多 2 個候選；第 3 個候選需使用者明示同意；
候選只做到足以比較的 spike，不在選出贏家前各自做完整 production hardening。
所有候選先經相同的機械驗證與比較 panel，只有暫定贏家進完整 code review；若贏家被退回，
修正後重審，或依原評判結果遞補下一名。落選分支保留評估紀錄，依取消流程詢問使用者後回收。

### 5.6 審查粒度（使用者已裁定，2026-08-27）

建議保留兩個不同目的的閘門：

1. **工單層**：每張工單各自對 AC、Write Scope 與測試做窄範圍 code review；沒有通過就不能併入輪次。
2. **輪次層**：所有工單進入輪次後，只做一次跨工單 panel，檢查契約一致性、重疊區、
   語意衝突與整合結果；使用者只接收一份統整報告。

競爭式候選在選出贏家前只走共同評判 panel，不要求每個落選 spike 都付一份完整 code review。
panel 的成員、context 隔離與報告查核方式由 DN-008 決定；本 DN 只定何時需要哪一層。

### 5.7 整合驗證與失敗退回（使用者已裁定，2026-08-27）

建議由 `qa-automation-engineer`（執行時路由到 `test_verification` 輪廓）負責輪次整合驗證。
時點在所有工單通過個別審查並進入輪次之後、輪次 panel 與主線合併之前；驗證對象必須是
「當下主線＋輪次」的整合候選，而不是只測已經落後的輪次 branch。

驗證失敗時主線保持不動，輪次也不得進入最終審查：

- 能歸因到單張工單的 AC／Write Scope：該工單從 `In Review` 退回 `In Progress`，
  恢復原 Task ID 分支與 worktree 修正，再重跑個別與整合驗證。
- 屬跨工單互動、不能誠實歸給單一 owner：開一張 integration-fix 工單，明列受影響 Contract
  與 Blocked By；若因此超過一輪 5 張上限，回到使用者重排，而不是偷偷突破上限。
- 原 Task ID branch 在整輪通過以前保留；工單併入輪次後可先移除 worktree，退回時再重建。

只有整合驗證與輪次 panel 都通過，才進入 DN-006 的最終人工閘門與主線 merge。

### 5.8 工作輪次的版控載體（使用者已裁定，2026-08-27）

轉寫畢業工單時發現：`Blocked By` 能表達工單間的邊，卻沒有任何版控資料回答
「這一輪包含哪 2～5 張工單、目標與 branch 是什麼」。只看目前 checkout 不成立——
branch 會刪除、不同 worktree 的 checkout 也不同，掃描器因而無法重建輪次、wave 與 review target。

| 方案 | 唯一來源 | 取捨 |
|---|---|---|
| A. 每張工單加 `Round` | 工單分散記 Round ID | 查單張容易，但目標、base SHA、封閉集合與整合狀態仍無處可放 |
| **B. Round Manifest（建議）** | `docs/development/rounds/{RoundID}.md` 集中列目標、branch、base 與 2～5 張 Task ID | 多一種 artifact，但輪次只有一份來源，工單不重複寫 Round |
| C. 只靠 branch／PR | Git ref 或平台資料 | branch 回收、換平台或離線後無法重建，不符合 DN-006 的可追溯要求 |

建議 B：全域 `ROUND-001` 起算，檔名可附 topic slug；manifest 保存目標、branch、開輪 base SHA、
封閉的 Task ID 清單與整合 Review Target。wave、反向 blocks 與狀態由工單和 Git 推導，
不手抄成第二份來源。DN-008 的 raw panel finding、reconciliation 與整合驗證也追加在同一份 manifest，
不另開 round review 檔，讓一輪的規劃與放行證據只有一個可攜載體。
