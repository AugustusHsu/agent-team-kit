## 1. 問題陳述

DN-003 已畢業，但它只定了**單線**的一層分支：`{TaskID}` → `main`，squash merge。
一旦有多個 agent 同時在跑，這個拓撲會缺三樣東西：

- **沒有中間層。** 所有工單分支都直接對著 `main`，`main` 成為唯一的整合點。
  同 Epic 的三張工單各自對 `main` 開 PR，彼此的中間狀態互相看不見，
  只能在 `main` 上事後撞。
- **沒有傳播機制。** DN-003 假設分支存活時間短、期間 `main` 不會動。
  並行之下 `main` 會在分支存活期間被別人改掉，而規範沒有規定
  「什麼時候該把 base 的新內容拉進來」，也沒規定誰負責。
- **沒有所有權概念。** 兩個 agent 同時改同一個檔案，DN-003 完全沒有話講。

## 2. 兩層分支拓撲（使用者的構想與收斂）

使用者提出的形狀：

```
main（或 master）
 └── feature/{module}          ← 模組分支，長期存活
      ├── {TaskID}-a           ← 工單分支，PR 進模組分支
      ├── {TaskID}-b
      └── {TaskID}-c
```

值得注意的是，這**不是新發明的結構**，而是 kit 既有 `Epic → 子工單` 模型
往 git 上的投影：模組分支 ≈ Epic 的作用範圍，工單分支 ≈ 子工單。
兩層的對應關係本來就在，只是之前沒有在 git 上表現出來。

### 2.1 兩層都保留分支拓撲（使用者已裁定，2026-08-27）

DN-003 的 squash-only 會在刪除 branch ref 後，使分支的過程 commits 失去可達路徑。
使用者要求「開出去的分支都能在 git history 中呈現」，因此合併策略不再取決於有沒有 PR 平台：

| 合併方向 | 策略 | 理由 |
|---|---|---|
| 工單分支 → 工作輪次分支 | **merge commit** | 保留每張工單的側支拓撲與過程 commits；輪次的 first-parent 仍是一張工單一行 |
| 工作輪次分支 → `main` | **merge commit** | 保留整輪與內層工單拓撲；主線 first-parent 仍是一輪一行 |
| 單張工單分支 → `main` | **merge commit** | 沒有中間層時仍保留該工單側支；主線 first-parent 是一張工單一行 |

PR／MR 繼續負責審查、CI 與權限閘門，**不再負責替 squash 接住歷史**。
分支 ref 刪除後名稱本身不會留在 Git 物件裡，所以每一顆 merge commit 的訊息仍必須寫入
Task ID 或輪次範圍；拓撲與訊息合在一起，才同時保得住形狀與名稱。

2026-08-27 在 `/tmp` 隔離 repo 實測兩張平行工單、主線同期前進與兩層 `--no-ff` 合併：
主線 first-parent 一輪一行、輪次 first-parent 一張工單一行、完整圖可展開兩條工單側支，
最後三條分支都能用 `git branch -d` 安全回收。代價是歷史保留更多 merge 與過程 commits；
乾淨視角改由 first-parent 提供，不再用 squash 在寫入時銷毀資料。

### 2.2 中間層邊界與啟用條件（使用者已裁定，2026-08-27）

中間層**不沿用永久的產品模組邊界**，而是一條短命的**工作輪次／主題分支**：

```
main（或 master）
 └── feature/{topic}          ← 一輪的整合分支，輪次結束即收尾
      ├── {TaskID}-a          ← 每張工單仍有自己的分支
      ├── {TaskID}-b
      └── {TaskID}-c
```

一輪只服務一個可說清楚的目標，含 **2～5 張相關工單**；工單集合原則上在開工前封閉，
不得把後來出現但與目標無關的需求持續塞進同一條分支。全部工單完成、取消或移出後，
輪次分支就失去存在理由，必須整合並收尾。

兩層拓撲是**條件式啟用**，不是所有開發的固定成本：

- 單張工單：維持 `{TaskID}` → 主線的一層拓撲。
- 同一目標有 2～5 張相關工單：啟用 `feature/{topic}` 中間層，每張工單仍保有獨立分支。

這仍然是「一套規則」：差別只是中間層的基數可以是零，不另寫一份單人流程。
工作輪次不必等同 Epic；Epic 是需求分類，輪次是一次有明確結束條件的整合範圍。

## 3. 變更傳播的 git 機制

對應 DN-005 §2.4 的場景：某個分支改了 spec／介面，其他分支要適應。

### 3.1 Stacked PR

業界對「B 依賴 A、兩者都還沒 merge」的標準答案是**堆疊 PR**：
A 的 PR 以 `main` 為 base，B 的 PR **以 A 的分支為 base**。
A merge 之後，B 需要 rebase 到新的 base 上，PR 的 diff 才會正確。

- [Graphite](https://graphite.com/blog/automatic-rebase-after-merge) 把這個 rebase 自動化了
  （merge 底層後自動 rebase 上層），**但只在從 Graphite app 按 merge 時生效**，
  從 GitHub 網頁 merge 不會觸發。
- 原生 GitHub **沒有**這個能力，每一次依賴與 rebase 都要手動管理。
- 實務回報自動化涵蓋約 8 成，其餘仍需人工解衝突。
  重複性衝突可以靠 `git rerere`（重用已記錄的解法）壓下來。

### 3.2 ⚠️ 與分支保護設定的已知衝突

**開啟「dismiss stale pull request approvals when new commits are pushed」
會讓堆疊 PR 無法經由 Graphite 合併**——因為 rebase 會推新 commit，
approval 隨即被作廢，形成循環。

§5 的設定表已經把這一項關掉。當時的理由是別的（單人 repo、approvals = 0 之下它沒有意義），
**但事後看剛好也擋掉了這個坑**。若未來因為任何理由想把它打開，
必須先確認堆疊 PR 是否還在用。

### 3.3 誰負責適應：依賴方

業界的所有權規則很一致：**rebase 依賴分支到更新後的 base，
由持有依賴分支的那一方（那個 agent）自己解衝突。**
理由是它才知道自己的變更意圖，上游沒有義務去猜下游要什麼。

這條直接回答使用者的「另一個分支/agent 需要對這個改動做適應」——
**適應是下游的責任，不是上游的**。上游的責任只到「把改動變成一個可被 rebase 的、
相容的 base」為止，也就是 DN-005 §3.2 的 expand 階段。

### 3.4 一輪多張工單的合併拓撲（2026-08-19 實例）

**這是 §3.1 的第一個本 repo 實例，也是 §7 待決事項第 4 條的第一份實證。**

2026-08-18 一輪清掉 `PEV-DEV-AGENT-030／029／025`。三張有真實的內容依賴——
029 改了四份 skill，025 又全面重寫同一批——因此開成堆疊分支
（030 ← 029 ← 025），依 `git_workflow.md` §8.3a 逐一 `--no-ff` 併回整合分支。

使用者看 `git log --graph` 後提出質疑：形狀是階梯狀的，
**「一輪多個工單應該只有一個 merge commit 才對」**。

#### 查證：功能面沒破，破的是圖形

| 檢查項 | 結果 |
|---|---|
| `--first-parent` 讀主線（§6.1／§8.3 定義的讀法） | ✅ 三行，每行帶 Task ID |
| 各 merge 的 first-parent diff | ✅ 030=6 檔、029=14 檔、025=36 檔，各自對應 |
| 側支邊界 `^1..^2` | ✅ 各自只含自己那顆工單 commit |

規範要求的一切都達成了。**問題純粹在拓撲形狀**，而形狀不是現行規範管的東西——
這正是本 DN 存在的理由。

#### 四種形狀的實測

沙盒建了四個等價的 repo（三張工單、同樣的依賴），對照 `git log --graph --oneline`：

| 形狀 | 做法 | 圖形 | `--first-parent` |
|---|---|---|---|
| **A** | 堆疊，不 rebase（本輪實際做法） | 階梯：一條側線被鉤三次 | ✅ 三行 |
| **B** | 平行，三條都從整合分支開 | **更亂**，多重交叉 | ✅ 三行 |
| **C** | 一輪一分支，一次合併 | ✅ 最乾淨 | ⚠️ 一輪一行（側支 Task ID 全保留） |
| **D** | 堆疊 ＋ 每次 merge 後 rebase 上層（§3.1 的做法） | ✅ 三個獨立側支泡泡 | ✅ 三行 |

#### 四個結論

> ⚠️ **結論 1 與 3 是 2026-08-19 稍晚更正過的版本。**
> 初版寫「形狀 C 不可行，是拿工單粒度換圖形」——**那個判斷是錯的**。
> 錯不在算錯代價，而在**沒去查**：沒實際看 C 的側支保留了什麼，
> 也沒查 `--first-parent` 到底有沒有東西依賴它。錯誤判斷不從本節刪除，
> 因為它正是本 DN 要記的那一類——看起來合理、推得也順，就是沒有去驗。

**1. 「合成一個 merge commit」是取捨，而代價比初版評估的小得多**（形狀 C）。

| 初版寫的 | 實際查證 |
|---|---|
| 工單粒度消失，主線上三張工單不可分辨 | **粒度沒消失**。側支三顆 commit 各自帶 Task ID 完整保留，`git log --graph` 與 `git log <merge>^1..^2` 都讀得到。變的是**讀法要換一個指令**，不是資訊沒了 |
| （隱含）`--first-parent` 一張工單一行很貴 | **零機器依賴**。全 repo 實查，它只出現在 `git_workflow.md` 的 137／303／313 三行**文字**、`PEV-DEV-AGENT-003`、以及本 DN。`precheck.py`、`scan_backlog.py`、`tests/` 全都沒用到——它是人讀慣例，不是閘門 |
| 只列了 C 的代價，沒列好處 | C **免除形狀 D 的全部 rebase 成本**，而且是結構性的免除，見結論 4 |

C 真正的代價剩兩項：`git bisect --first-parent` 第一階段的粒度從工單降到輪次
（本 repo 是文檔專案，實務上用不到）；以及 `git branch -d` 一次代表整輪——
後者已由使用者裁定拆解，見下方「本輪的處置與裁定」。

**2. 平行分支不是答案**（形狀 B）。反直覺的實測結果：三條分支都從整合分支開，
圖形交叉**比堆疊更亂**。而且有內容依賴時根本開不出來——029 與 025 改同一批檔案，
平行開必然衝突。

**3. 形狀 D 可行，但不是最省的**。§3.1 早就寫明「A merge 之後，
B 需要 rebase 到新的 base」，本輪漏掉了這一步——形狀 A 的階梯就是這麼來的。
補上之後圖形乾淨、`--first-parent` 保住三行，各 merge 的 diff 範圍與最終檔案內容都正確
（沙盒驗證：三次 rebase 後共用檔內容為最後一張工單的版本，未丟失任何變更）。
**D 沒有錯，只是 C 用更少的動作達到同一種可讀性。**

**4. rebase 的需求來自「中途 merge」，不是來自「堆疊」**。這是 C 與 D 成本差異的
**全部**來源，而初版完全沒說出來：

- 堆疊分支之所以要 rebase，是因為**下層 merge 回主線後 base 前進了**，上層的 base 過期。
- 形狀 C 同樣是堆疊做出來的（030 → 029 → 025 依序疊在同一條分支上），
  但它**中途不 merge 回主線**——base 從頭到尾不動，沒有任何東西會過期，rebase 需求歸零。

所以 §7 第 4 條掛著的「未量到的真實衝突下 rebase 成本」，在形狀 C 下
**不是被解決，是被繞開**。這個區別要留著：哪天真的需要中途把某張工單先合進主線
（例如那張要先上線），這筆成本會原封不動回來。

#### rebase 的代價，以及一個既有規範剛好擋掉的坑

rebase 會**改寫 commit SHA**。兩個後果：

- 分支若已推送，需要 force push（本 repo 走 §8.3a 無遠端 PR，暫時不痛）。
- 工單裡若記了 commit SHA，rebase 後全部失效。
  ——**`git_workflow.md` §6.3 明訂「回填 PR 編號，不是 commit SHA」，這個坑已經被擋掉了。**
  當初那條的理由是別的（SHA 在 squash 後會變），事後看剛好也涵蓋 rebase。
  這與 §3.2 是同一個模式：**為了 A 理由做的決定，剛好擋掉了 B 坑。**

**未量測的成本**：本輪三張的 rebase 在沙盒裡沒有衝突（改動可整檔覆寫），
但真實情況下 029 與 025 改的是同一批 skill，rebase 至少要人工解一次衝突。
**「人工維護依賴鏈的成本」正是 §7 第 4 條懸而未決的那一項，本輪沒有量到。**

#### 本輪的處置與裁定

使用者 2026-08-19 分兩次裁定。

**第一次——不重寫已合併的那三顆 merge commit。**
理由是功能面三項驗證全部正確，差別只在圖形；而「正確形狀」當時在 §7 仍是待決項，
現在重做等於用一個尚未裁定的形狀，覆蓋掉唯一的實例證據。

**第二次——採用形狀 C 並立法。** 看過四種形狀的實測後裁定：
一輪多張工單走**一條分支**，側支保留各工單自己的 commit，主線只有**一顆** merge commit。

**第三次——形狀 C 擴充為巢狀拓撲（2026-08-27）。** 主線仍只有一顆輪次 merge，
但輪次內每張工單改以自己的 merge commit 進入，不再把所有工單 commits 排成無邊界的直線。
這保留 C 的主線視角，同時讓每條實際開出的工單分支都在 Git 圖上有獨立側支。
連帶裁定 `Done` 訊號的拆解——

| 原本 | 裁定後 |
|---|---|
| `git branch -d` 成功 = 該工單 `Done`（§6.4／§8.3a） | `git branch -d` 成功只證明**輪次已合併** |
| （無獨立的工單完成訊號） | **工單是否完成，改由合併前逐張確認 AC 與審查檔** |

拆解之所以成立，關鍵在審查檔 `docs/features/<模組>/reviews/<TaskID>.md`
**本來就是一張工單一份**，不隨拓樸改變——逐張確認的載體一直都在，
只是以前借用了 `branch -d` 這個順手的訊號，於是兩件事被綁成一件。

（該節目前整節為空，原文即寫明「定案後補入本節」）。
**已合併的那三顆 merge commit 仍不重寫**——第一次裁定不受第二次影響。

## 4. 隔離與所有權

### 4.1 ⚠️ worktree 不解決所有權問題

一個常見誤解，值得單獨標記：

> worktree 本身不解決所有權。如果兩個 agent 都有權限修改同一個共用檔案，
> 有沒有 worktree 都會衝突。

worktree 提供的是**工作區隔離**（各自有獨立的檔案系統與 HEAD），
不是**衝突避免**。學界的說法更直接：git worktree 只提供低層次的工作區隔離，
它不解決任務拆解、依賴追蹤、語意衝突與合併取捨。

這對本 repo 有直接意涵：kit 的 worktree 規範已於 2026-08-16 整份移除（DN-003）。
日後要不要重新引入，**必須連同所有權規則一起設計**，只把 worktree 加回來等於沒加。
Claude Code 能為 subagent 提供 worktree 隔離；Codex App 也能建立受管理的 worktree，
並在 Local／Worktree 間 Handoff。各產品的操作面不同，但都沒有解決所有權問題。
本檔只定 provider-neutral 的 git 不變式；執行時選哪個 surface 由
[DN-009](DN-009_multi_agent_capability_routing.md) 路由。

**2026-08-27 裁定：worktree 條件式恢復。** 同時執行兩張以上工單時，
每條活躍工單分支使用一個 worktree；單張或依序執行時不強制增加工作區。
建立 worktree 之前必須先完成下節的 `Write Scope` 檢查，不能拿工作區隔離代替所有權。
工單併入輪次後移除自己的 worktree；輪次收尾時只能剩主工作目錄。

### 4.2 檔案所有權與重疊區

主流做法是 **one file, one owner**，通常落在**目錄層級**
（前端 agent 擁有 `src/components/`，後端 agent 擁有 `src/api/`，
測試 agent 只寫 `src/__tests__/`），共用檔案指派給單一 agent。

補強機制是 **重疊區登記（overlap zone registry）**：列出高影響檔案。
常見的重疊區是路由表、設定檔、元件註冊表、DB migration、API 契約定義。

本 repo 的重疊區實測（跨工單被反覆修改的檔案）：

| 檔案 | 狀態 |
|---|---|
| `docs/DOCS_MAP.md` | 熱點，每次新增文件都要改 |
| `README.md` | 熱點 |
| `kit/.agent/resources/team_protocol.md` | 熱點，且有指路檔要同步 |
| `docs/development/BACKLOG.md` | **已解決**——改由 `scan_backlog.py` 生成，不手改 |

`BACKLOG.md` 的解法值得注意：**把熱點檔變成生成物**，衝突就從「人工協調」
降級成「重跑腳本」。這是比登記制更根本的一招，但不是每個熱點都適用。

**2026-08-27 裁定：動態所有權與靜態風險分開記。**

- 每張工單新增結構化 `Write Scope`；進入多工單輪次時必填路徑／glob，表示該輪的動態所有權。
  Epic 不承載所有權，因為需求分類與工作輪次不是同一個邊界。
- 另設專案級、版控內的 `overlap zones` 登記檔，記錄跨輪次都成立的長期高風險區。
  它不是某張工單的所有權清單，兩者不得互相取代。

兩張工單的 `Write Scope` 重疊時，**預設不得並行**：改由單一 owner 依序處理，
或先拆出共用契約工單。確實無法避免時才登記例外，由 AI panel 先產出可回查的風險報告，
人工判斷集中在輪次整合點一次完成，不要求使用者逐張重讀全部 diff。

安全政策、公開 API、資料庫 migration 等關鍵 `overlap zones` 是例外：即使只有一位 owner，
最終整合仍保留人工閘門。panel 是前置分析與縮小判讀範圍，不能取代這類風險的使用者裁定。

**`git rerere` 的定位**：只列為 repo-local 選用加速器，不成為 kit 預設。
啟用後每次重用衝突解法仍須檢查 diff、重跑測試；`.git/rr-cache` 不進版控。
它可以降低重複解衝突的成本，但不能把過期解法升格成規格。

### 4.3 長命分支的漂移

模組分支長期存活會累積漂移。實測參考（`../my_workstation` 的
`feature/labeling-viewing-system`）：存活 24 天、領先 `master` 235 顆 commit、
涉及 132 張工單、464 個檔案、+57,967 行，而 **behind master = 0**。

behind = 0 是因為那個 repo 是單線的，`master` 期間沒有別人在動。
**一旦並行，這個數字不會再是 0**，業界對長命分支的警告届時就會開始適用。
所以模組分支的存活上限與定期回吸 `main` 的規則，是這個拓撲成立的必要條件，
不是可選的最佳實務。

**2026-08-27 裁定**：用短命工作輪次取代長命模組分支後，不設「每 N 天」的日曆式回吸。
生命週期與同步都改由事件觸發：

1. 開輪前從最新主線建立輪次分支。
2. 主線若出現與本輪重疊、且本輪不能忽略的必要變更，暫停受影響工單，由依賴方適應後再繼續。
3. 全輪整合回主線前，必須以當下主線做一次整合驗證。

一輪的硬邊界是「一個目標、2～5 張工單、集合原則上封閉」；不以天數代替範圍治理。
這讓短任務不會因碰到任意日曆門檻而被迫重寫歷史，也阻止輪次分支變成永久開發線。

## 5. 分支保護設定（使用者已裁定，2026-08-16）

| 設定 | `main`／`master` | `feature/**`（工作輪次分支） |
|---|---|---|
| Require a pull request | ✅ | ✅ |
| Required approvals | **0** | **0** |
| Required checks | 全套（含 integration／e2e） | 快測（unit + lint） |
| 合併方式 | **merge commit** | **merge commit** |
| Dismiss stale approvals | ❌ 關 | ❌ 關 |
| Do not allow bypassing | ❌ 不開 | ❌ 不開 |

三個必須連帶記住的理由，否則日後會有人「好心」改錯：

- **`Required approvals` 必須是 0。** GitHub 禁止 PR 作者核可自己的 PR，
  本 repo 只有一名協作者，設成 ≥ 1 是**永久死鎖**，不是嚴謹。
- **分支樣式必須寫 `feature/**`，不能寫 `feature/*`。** GitHub 用
  `File::FNM_PATHNAME` 比對，單顆 `*` **不跨 `/`**，`feature/*` 會漏掉
  `feature/foo/bar` 這類名稱。
- **`Dismiss stale approvals` 關閉**——理由見 §3.2。

本 repo 目前只需要 `main` 這一組；`feature/**` 那組要等工作輪次分支真的存在才設。

  本 repo 的實證（2026-08-17 盤點）：
  - 一生只開過三個工作分支，只有 `PEV-DEV-AGENT-001` 在 history 上看得到
