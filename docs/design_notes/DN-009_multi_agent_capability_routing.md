# [DN-009] 多代理能力路由與可用性

**🚥 狀態 (Status):** 🔍 Exploring
**📅 建立 (Created):** 2026-08-26
**🔗 依賴 (Depends on):** DN-001（本檔的格式與畢業條件）
**📌 來源 (Origin):** 使用者指令（2026-08-26）——專案已確定混用 Claude Code 與 Codex，未來還會加入其他廠商；要求預設開發流程能依任務選擇執行者，並處理只有單一訂閱、訂閱中途失效與人工覆寫
**🤝 姊妹篇 (Sibling):** DN-010（跨代理入口與設定分層）；DN-011（初始化、健康檢查與生命週期）

> 本檔只定路由模型；設定放哪裡由 DN-010 決定，狀態怎麼探測與更新由 DN-011 決定。

## 1. 問題陳述

本專案現在已由 Claude Code 與 Codex 交替執行，但 kit 的模型仍只有兩個維度：

- `Assignee` 指定角色／skill，例如 `tech-lead`、`backend-developer`；
- `Task Type` 指定佇列，例如 `queue_agent`、`queue_backend`。

兩者都答不出「這張工單此刻該交給哪個產品、在哪個介面執行」。直接把廠商寫進
`Task Type` 也不成立：同一張實作工單可以由 Claude Code CLI 或 Codex CLI 完成；
同一個 Codex 又有 CLI、App Local、App Worktree、Cloud 等能力不同的執行面。

路由還受到**會變動的外部狀態**影響：使用者可能只有一個訂閱、額度暫時耗盡、登入失效、
GitHub Connector 尚未連結，或工作做到一半才失去某個執行面。如果規則只記「偏好 Codex」，
它無法回答這些失效情境；如果只記「目前可用 Claude」，隔天續訂後又會成為過期資訊。

## 2. 已查證的現況

### 2.1 供應商與執行面不是同一個概念

| 供應商 | 執行面 | 已知特性 |
|---|---|---|
| Anthropic | Claude Code CLI | 本機互動、非互動輸出、subagent／平行執行能力 |
| OpenAI | Codex CLI | 本機互動、`exec`／`review` 等可腳本化入口 |
| OpenAI | Codex App Local | 直接在目前專案目錄工作 |
| OpenAI | Codex App Worktree | 由 App 管理隔離工作區與 Handoff |
| OpenAI | Codex Cloud | 在已設定的遠端環境執行，GitHub 連結是另一項前提 |

因此「Claude 還是 Codex」與「CLI 還是 App／Cloud」是兩次不同的選擇，不能壓成一欄。

### 2.2 2026-08-26 本機探測樣本

| 能力 | 結果 | 不能推出的結論 |
|---|---|---|
| `claude auth status` | 已登入，`subscriptionType=max` | 不代表每次請求都不會遇到額度／服務錯誤 |
| `codex login status` | 已用 ChatGPT 登入 | 沒有提供訂閱到期日 |
| GitHub SSH | `AugustusHsu` 驗證成功 | 不代表 Codex Cloud 的 GitHub Connector 已連結 |
| `gh api user` | 回傳 `AugustusHsu` | `gh auth status` 同時仍誤報舊 token 無效 |
| ChatGPT 瀏覽器設定頁 | 該瀏覽器 session 未登入 | 只能記為 `unknown`，不能判成 Connector 不存在 |

最後兩列是重要反例：**狀態命令與功能探針會互相矛盾**，路由不能只讀一個布林值。

### 2.3 與現有 DN 的邊界

- DN-005 決定工單與依賴怎麼拆；本檔只接收拆解後的**能力需求**。
- DN-006 決定 git 拓撲與隔離；本檔只選擇能滿足該隔離要求的執行面。
- DN-008 決定 panel 與 context 隔離；異質 panel 可以由不同廠商組成，但路由判準由本檔提供。

## 3. 已定調的設計

### 3.1 四個維度必須分開

| 維度 | 回答的問題 | 例子 |
|---|---|---|
| **角色 (Role)** | 要用哪一種專業判斷 | `tech-lead`、`security-engineer` |
| **任務輪廓 (Task Profile)** | 這次工作需要哪些能力與風險限制 | `implementation_local`、`review_security` |
| **執行設定檔 (Execution Profile)** | 哪個產品、哪個執行面與其工具集合 | `claude-code-cli`、`codex-app-worktree` |
| **可用性 (Availability)** | 這個設定檔此刻真的能不能用 | `verified`、`degraded`、`unavailable`、`unknown` |

`Assignee` 繼續表示角色，**不改成廠商名稱**。使用者換訂閱不應迫使工單換負責角色。

### 3.2 任務宣告能力，不宣告廠商

任務輪廓以能力需求描述，例如：

- 必須能讀寫本機 repo、執行 shell 與測試；
- 必須有獨立 context 或 worktree；
- 必須能操作瀏覽器／桌面應用；
- 必須能以非互動模式輸出結構化結果；
- 不得把程式碼送到 cloud；
- 必須有人在場完成視覺驗收。

廠商名稱只出現在執行設定檔。新增第三家供應商時，只要增加設定檔，不改任務語意。

### 3.3 路由順序

候選執行設定檔依下列順序過濾與排序：

1. **硬性能力**：缺任何一項就淘汰，不得降級猜測。
2. **安全與資料政策**：例如禁止 cloud、禁止外部 Connector。
3. **當下可用性**：只讓功能探針仍有效的候選進入排序。
4. **專案偏好**：專案可偏好某個供應商／執行面，但不能推翻前 3 項。
5. **成本、速度與 context 需求**：只在合格候選之間比較。
6. **使用者當次覆寫**：最後決定權仍屬使用者，且只影響明示範圍。

候選為零時要回報「缺哪項能力」，不得靜默改用不符合要求的執行面。

### 3.4 初始任務輪廓

| 輪廓 | 典型工作 | 核心能力 |
|---|---|---|
| `design_research` | DN、架構比較、外部證據 | 大量閱讀、來源查證、長 context |
| `implementation_local` | 程式與文件實作 | repo 讀寫、shell、測試 |
| `parallel_long_running` | 多工單、背景任務 | 隔離工作區、持續執行、可交接 |
| `review_security` | code review、安全審查 | 新鮮 context、唯讀 diff、證據紀錄 |
| `test_verification` | 測試、負向對照 | 原始輸出保真、exit code、可重跑 |
| `visual_interactive` | UI、瀏覽器、桌面應用 | 視覺操作、即時使用者驗收 |
| `automation_batch` | CI、批次、固定流程 | 非互動模式、結構化輸出、timeout |
| `external_integration` | GitHub、MCP、Connector | 已驗證的外部連線與權限 |

這是可擴充 registry 的第一批資料，不是寫死在程式碼裡的 enum。

### 3.5 可用性不是訂閱名稱

路由只依賴「某項能力最近一次是否驗證成功」，而不是猜測方案名稱的含義。
方案名稱、使用者填的到期日可作提示，但不能取代功能探針。

可用性至少要能區分：

- `verified`：功能探針成功且仍在有效期內；
- `degraded`：部分能力失效，但仍可執行受限任務；
- `unavailable`：已確認無法登入、無權限、額度不足或工具缺失；
- `unknown`：從未驗證、驗證過期，或通道本身不可觀察。

### 3.6 中途失效採「保存 → 重探 → 重新路由」

執行者中途失效時不重開工單、不改 `Assignee`，而是：

- 保留目前分支／worktree 與可重現的未完成狀態；
- 記錄最後成功驗證點、失效原因與尚未完成的 AC；
- 重新探測候選執行設定檔；
- 由另一個合格執行者接手同一張工單。

這裡只定狀態語意；實際承載與命令由 DN-011 決定。

### 3.7 每次路由都要可解釋

審查紀錄至少要能回答：任務被分類成什麼、硬性能力有哪些、選了哪個設定檔、
其他候選為何被排除、是否發生中途交接。不得只記「這次用 Codex」。

## 4. 待決事項

| # | 待決 | 選項 | 建議 |
|---|---|---|---|
| 4.1 | 任務輪廓如何擴充 | 寫死 enum／版本化 registry | **registry**；新增類型不必改路由核心。反方：需要 schema 與相容性規則 |
| 4.2 | 能力詞彙的粒度 | 高階能力／逐工具列舉 | 以高階能力為主、工具為證據；逐工具會隨產品版本快速腐爛 |
| 4.3 | 合格候選如何排序 | 固定優先序／加權評分／純人工 | 固定分層過濾＋層內簡單評分；全自動分數難解釋，純人工則沒有路由價值 |
| 4.4 | 工單要不要新增必填欄位 | 全部必填／只有例外才寫 | 保留現有 `Task Type`／`Assignee`；能力需求由輪廓給預設，工單只寫 override |
| 4.5 | 使用者覆寫有效多久 | 單次／整輪／專案永久 | 預設單次；整輪或永久必須明示，避免一次選擇變成陳舊政策 |
| 4.6 | cloud 與資料敏感度如何表達 | 單一允許開關／分級 | 分級；「可上 cloud」與「可連外部 Connector」不是同一件事 |
| 4.7 | 只有一個供應商時是否仍跑路由 | 略過／照跑 | 照跑但只剩一個候選；仍需確認能力足夠，不能把「有訂閱」等同「能做」 |
| 4.8 | 路由決策寫在哪 | 工單／審查檔／獨立日誌 | 工單只寫穩定需求，審查檔寫本次決策；機器狀態另由 DN-011 管 |
