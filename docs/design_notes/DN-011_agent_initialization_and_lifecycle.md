## 1. 問題陳述

現行 `install.sh` 只做安全複製與 manifest 升級。首次安裝結束後，它印出四條人工步驟，
其中只有「填 `CLAUDE.md`」，沒有：

- 偵測 Claude／Codex／其他執行者是否安裝與登入；
- 區分 CLI、App Local、Worktree、Cloud 與 Connector 能力；
- 產生跨代理入口、專案路由政策與使用者本機狀態；
- 驗證「狀態命令說已登入」是否真的能完成所需操作；
- 在訂閱過期、額度不足或中途失效時更新資訊並交接。

若把這些全部塞進 `install.sh`，安裝會從「可離線、可預測的檔案複製」變成依賴網路、登入、
互動式選項與各家 CLI 版本的易碎程序；若完全不管，使用者每個專案都要重新發明設定流程。

## 2. 已查證的事實

### 2.1 安裝與初始化的生命週期不同

| 動作 | 輸入 | 可否離線 | 產物歸屬 |
|---|---|---|---|
| 安裝／升級 kit | `kit/` 與 manifest | 可以 | 共享骨架與可升級規範 |
| 初始化代理 | 專案需求、使用者選擇、本機工具 | 不一定 | 專案政策＋使用者執行狀態 |
| 健康檢查 | 已設定的 execution profiles | 視 probe 而定 | 時效性狀態，不是規格 |
| 路由 | 工單需求＋專案政策＋最新狀態 | 可以讀 cache | 一次性的選擇與解釋 |
| 遷移 | 舊入口、舊設定與新模板 | 可以先 dry-run | 人工確認後的新設定 |

兩者混成一支命令會讓 `--upgrade --dry-run` 也可能觸發登入或外部連線，破壞現行保證。

### 2.2 狀態查詢不是健康檢查

2026-08-26 實測同時得到：

- `gh auth status` 報 token 無效；
- `gh api user` 卻成功回傳登入身分；
- GitHub SSH 驗證也成功。

所以健康檢查至少需要「中繼資料」與「最小功能探針」兩種證據，矛盾時不能擅自選一邊。
同理，`codex login status` 只證明有登入資料，不證明 cloud repo、額度或特定 plugin 可用。

### 2.3 有些能力無法無副作用自動探測

| 能力 | 可自動探測程度 | 限制 |
|---|---|---|
| CLI 是否安裝、版本 | 高 | 不需網路 |
| auth metadata | 中 | 可能過期或誤報 |
| 最小 API read | 高 | 需要網路，可能受 rate limit |
| 訂閱到期日／剩餘額度 | 低 | 各產品未必提供穩定機器介面 |
| App Connector | 中 | 可能需要已登入的 UI 或一次 cloud task |
| push／寫入外部服務 | 不應自動 | 有外部副作用，必須另行授權 |

因此狀態模型必須容許 `unknown`，不能為了填滿表格而假裝知道。

## 3. 已定調的設計

### 3.1 安裝器保持單純，初始化另成一層

`install.sh` 繼續只負責檔案與 manifest。安裝完成後可以**提示**初始化，但不自動登入、
不打外部 API、不替使用者選供應商。多代理初始化由獨立的標準工具處理。

### 3.2 管理介面需要六個動作

| 動作 | 職責 |
|---|---|
| `init` | 建立專案的共同政策，選擇要啟用的 provider／surface，產生入口候選 |
| `doctor` | 檢查安裝、版本、設定分層、登入與功能探針，清楚區分規格錯誤與環境錯誤 |
| `refresh` | 重跑到期或指定的探針，更新使用者本機狀態 |
| `route` | 對一張工單套用 DN-009，輸出建議與排除理由，不直接開工 |
| `explain` | 說明某個 profile 為何可用／不可用、狀態證據來自哪裡 |
| `migrate` | 把單一供應商或舊 schema 專案轉成新版，先產生差異、不可直接覆蓋種子檔 |

這些是管理能力，不代表一定要做成六支腳本；命令外形仍是 §4 待決。

### 3.3 初始化分成「共享政策」與「本機啟用」

專案可以宣告允許 Claude Code 與 Codex，也可以偏好某個 profile；但每位使用者只啟用自己
實際擁有的訂閱與執行面。同一份 repo 在 A 的電腦上可有兩個候選，在 B 的電腦上只有一個，
共同政策仍完全相同。

### 3.4 健康檢查以功能探針為主，狀態命令為輔

每個 adapter 定義：

- 零網路的安裝／版本檢查；
- 無外部寫入的最小 auth／read probe；
- 不能自動驗證的能力與人工確認方式；
- 成功、可重試、需重新登入、無權限、額度不足等錯誤分類；
- probe 的成本與建議有效期。

探針不得自動 push、開 PR、傳訊息、改 Connector 或購買／續訂方案。

### 3.5 可用性紀錄不保存憑證

本機狀態只記：profile、狀態、能力、證據摘要、最後驗證時間、建議下次驗證時間、
錯誤分類與使用者暫時停用期限。token、cookie、SSH 私鑰與完整命令輸出不進該檔。

### 3.6 更新觸發點

以下任一事件都應使相關 profile 重新驗證：

- 首次 `init` 或 clone 到新機器；
- 使用者新增／取消／續訂方案；
- 登入、模型、Connector、MCP 或 project environment 被改動；
- 狀態超過 adapter 的有效期；
- 執行中收到 auth、quota、permission、network 或 capability mismatch；
- 使用者明示 `refresh`。

不能觀察到訂閱到期日的 provider，採「到期前無法預知、失效時立即重驗」而不是猜日期。

### 3.7 中途失效的安全交接

失效處置遵守 DN-009 的「保存 → 重探 → 重新路由」，並要求交接資料至少包含：

- Task ID、branch／worktree、目前 HEAD 與工作區狀態；
- 已完成／未完成的 AC；
- 已跑過的驗證與最後可信輸出；
- 失效類型與哪個 profile 被停用；
- 接手者需要重跑的最小驗證。

交接本身不得繞過 `team_protocol.md` §1.10 Commit 閘門，也不得因換代理就把未完成工單標 Done。

### 3.8 遷移必須保留使用者客製內容

單一 `CLAUDE.md` 專案升級到雙入口時，`migrate` 只能提出候選與差異：

- 辨識哪些段落是共同規則、哪些是 Claude 專屬；
- 產生新的共同入口與 adapter 候選；
- 對既有檔案做三方比較或另存 `.new`；
- 由使用者確認後才取代專案入口。

不能因 kit 新增 `AGENTS.md` 就覆蓋使用者已由 Codex `/init` 產生的檔案。

## 4. 待決事項

| # | 待決 | 選項 | 建議 |
|---|---|---|---|
| 4.1 | 管理工具的外形 | 多支腳本／單一 `agent_runtime.py` 子命令／依賴外部 CLI | 建議單一 stdlib-only 腳本＋子命令，沿用 kit 可離線出貨原則；反方是檔案可能變大 |
| 4.2 | 使用者狀態放哪 | repo 內 gitignored／使用者全域目錄／兩層 | 兩層：帳號能力在使用者全域，project override 在 repo-local；要解 worktree 複製與專案識別 |
| 4.3 | `init` 互動程度 | 全互動／旗標優先／設定檔優先 | 互動與可重跑 flags 都要有；預設互動，CI／大量專案可用非互動模式 |
| 4.4 | probe 有效期 | 固定 24 小時／adapter 各定／每次 route 都跑 | adapter 各定；CLI 安裝可久、網路 auth 要短、昂貴 probe 不應每次跑 |
| 4.5 | 路由是否允許使用過期 cache | 一律禁止／可降級使用／依風險 | 依風險；本機純讀可用 `unknown` 候選，cloud 寫入不可 |
| 4.6 | App Connector 怎麼驗 | 讀設定 UI／跑最小 cloud task／只靠人工勾選 | 自動讀得到就讀，否則 `unknown + 人工確認`；不可為健康檢查製造遠端副作用 |
| 4.7 | 訂閱到期資訊如何輸入 | 強制日期／選填日期／完全不記 | 選填；日期只決定提前提醒，真正可用性仍以 probe 為準 |
| 4.8 | 中途失效是否自動換代理 | 全自動／先停下等待／依風險 | 預設提出重路由建議並等待；純讀、無外部副作用的子任務可由政策允許自動接手 |
| 4.9 | `precheck.py` 要檢查什麼 | 連本機狀態一起查／只查版控政策／不加入 | 只查 schema、引用與機密未入版控；本機訂閱狀態不能成為 CI 結果的一部分 |
| 4.10 | 初始化完成的最低門檻 | 至少一個 profile verified／所有宣告 profile verified | 至少一個能完成本機開發的 profile；其餘可 `unknown`，但 route 不得選它 |
