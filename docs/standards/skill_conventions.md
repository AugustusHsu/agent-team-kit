# Skill 撰寫標準 (Skill Conventions)

> **適用對象**：`.agent/skills/*/SKILL.md`——給 agent 讀的角色執行指引。
> **不適用**：BRD／PRD／ADR 等產出文件，那些歸
> [documentation_conventions.md](documentation_conventions.md)。
> 兩者讀者與生命週期不同，所以分兩份。

本標準只回答**「skill 該怎麼寫」**。**流程本身是什麼**寫在
`.agent/resources/team_protocol.md`（正版），本檔重疊處只指路、不複述。

每一條規則後面都附**「不寫這條會出什麼錯」**與真實案例。寫不出案例的規則不收。

---

## 1. 引用格式：`team_protocol.md §X.Y 章節標題`

引用守則時**檔名、編號、標題三者齊全**，只寫這一種：

```markdown
依 `team_protocol.md` §1.10 Commit 閘門，進入主線前要先取得同意。
```

同一句連續引用多節時，檔名寫在第一個編號前即可：
`team_protocol.md §1.9 程式碼隔離與分支、§1.10 Commit 閘門`。

**不寫會出什麼錯**：守則重編號時，**編號幾乎總是還在，錯的是它現在指向誰**。
DN-004 §4 附錄用丟棄式原型實跑過：在「§1.9 後插入一節、後續各往下推一格」的情境中，
4 筆 `§1.12` 引用當場指到「文檔權威階序」而非「取證通道保真」，
而只比對編號的檢查**仍然全綠**。標題是唯一會在重編號時轉紅的欄位。

自動檢查：`test_skill_引用守則的編號與標題都要對得上`。它以「往前找最近提到的檔名」
歸屬——這是「檔名只寫一次」那條慣例的代價，也是下一節存在的理由。

## 2. 自我引用寫「本篇第 N 節」，不得用裸 `§X.Y`

指 skill **自己**的章節時寫「（形式見本篇第 3 節）」，
**不要**寫 `§3`／`§8.1`。

**不寫會出什麼錯**：檢查以「往前找最近的檔名」歸屬引用，而 `team_protocol.md`
通常在檔案開頭就出現過，於是自我引用會被判成**指向守則**。
`PEV-DEV-AGENT-027` 實測踩到：`qa-automation-engineer/SKILL.md` 的 `:54` 與 `:225`
用裸 `§8.1` 指本篇自己，兩筆都被回報成「引用了不存在的 §8.1」。

該工單比較過改判準（限同一行內歸屬）：誤判會消掉，但**同時漏掉
`code-reviewer:17` 那筆真實的跨行引用**（路徑在第 16 行、編號在第 17 行）。
用真實覆蓋換誤判不划算，所以**改的是寫法不是判準**——
現行 13 份 skill 本來就全部沒有自我引用，這條只是把既有慣例寫下來。

## 3. 必備章節：分層，不是逐份清單

| 層 | 章節 | 誰要引用 |
|---|---|---|
| **全員** | §1.10 Commit 閘門 | 13 份全部 |
| **全員** | §1.11 文檔權威階序 | 13 份全部 |
| **全員** | §1.12 取證通道保真 | 13 份全部 |
| **施工側** | §1.5 狀態更新操作方式、§1.9 程式碼隔離與分支 | 實際跑工單狀態機與分支的角色 |

**為什麼 §1.10 是全員**：`PEV-DEV-AGENT-028` 盤點時，13 份 skill 分裂成兩個世界——
6 份施工側引用 §1.5／§1.9／§1.10，7 份上游側只有 §1.12。
但**上游側的產出（BRD／PRD／HLD／wireframe）一樣要進 commit**，
所以「它們不需要 commit 閘門」這個推論不成立。判準是**有產出就會 commit**，
與角色是不是寫程式無關。

**為什麼 §1.9 只到施工側**：分支操作與狀態機轉移只有實際跑流程的角色會做，
不必全員背；上游側需要時循 §1.11 的指路找過去即可。

**不寫會出什麼錯**：缺口不是「舊檔案沒跟上」那麼單純。§1.11 是 **0/13**——
一條對所有角色零覆蓋的規範等於不存在；而 §1.10 缺的 8 份裡包含 `scrum-master`，
它是流程詞最密的一份。**缺口跨越了「複檢過與否」這條線**，
所以逐份補會補成十三種寫法，必須先有一張分層表才知道補什麼。

## 4. 技術棧中立：第 1 層不寫死框架

skill 是 kit 出貨內容（第 1 層），**不得寫死特定框架、工具或指令**。
需要示例時寫「依專案實際技術棧」，把選型交給專案自己的第 2 層文件
（`devenv_spec.md`、`qa_testing_spec.md` 等）。

**不寫會出什麼錯**：`qa-automation-engineer/SKILL.md` 原本有一句
**「不可自行引入其他框架」**，前提是該專案用 Pytest／Cypress。
裝進非 Python 專案時，這句話會讓 agent **擋掉專案實際的選型**——
規範從幫忙變成阻礙。`PEV-DEV-AGENT-027` 移除該句並抽走 107 行綁定框架的程式碼範例。

**界線：frontmatter 的 `description` 不受此限。** 那一欄是 skill 的**觸發關鍵字**，
框架名列得越全、召回越準，與「規定專案該用什麼」無關。
本條管的是**正文裡的指令性句子**——判準是把該句放進另一個技術棧的專案，
agent 會不會因此做錯事。舉例句（「例如 `pytest` 建議或一組 `curl` 指令」）
落在中間：只要句型是「例如」而非「應使用」，就不會擋掉選型，可以留。

## 5. 標了「適用全角色」的守則章節：先補齊，再標記

守則章節一旦標上「適用全角色」，`test_適用全角色的章節被十三份_skill_全部引用`
就要求 13 份 skill 全數引用它。

⚠️ **順序不能顛倒**：**先把 13 份補齊，最後才標記**。
反過來做的話，標記那一刻 CI 立刻產生 13 筆紅，而補寫是另一件事的工作量。

**不寫會出什麼錯**：`PEV-DEV-AGENT-023` 把 §1.12 從 §2.3（只綁審查者）
升級成全角色時，要手動補 13 份——**漏掉任何一份都不會有執行期錯誤**，
那份 skill 只是安靜地不知道這條規範存在。該檢查就是為此而寫。

**這條檢查的已知邊界**：它依賴規範作者記得寫「適用全角色」那四個字。
沒標記的章節抓不到，所以它防的是「規範標了但 skill 沒跟上」，
**不是**「作者忘了標適用範圍」——後者是設計決定，沒有機器判準。

## 6. §1.12 段落必須角色專屬

每份 skill 的取證通道保真段落，要寫出**這條規範對「你這個角色」特別危險在哪**，
**不得套用他人句型**。

**不寫會出什麼錯**：`PEV-DEV-AGENT-025` 驗證時發現 `backend-developer` 與
`frontend-developer` 的該段落**除角色名外逐字相同，共同子字串 75 字**——
是更早以前留下的複製貼上。兩份已各自改寫，最長重疊降到 17 字。
複製貼上的段落讀起來像有規範，實際上沒有針對該角色的任何判斷。

**本條刻意不設機器判準。** `025` 用過「最長共同子字串 ≤ 12 字」，
但那個門檻是**判斷不是事實**——該工單審查檔已誠實記錄「12 字是寫檢查時訂的，
看到結果後沒有調降」。改寫後仍有 7 對超過 12 字，逐對檢視都是**規則原文的複述**
與**共用的條目標題**，不是共用的角色論證。**這條規則的判準本身就需要人讀過才能判**，
硬化成閘門只會製造誤報。要不要進自動檢查是另一個決定，本標準不預設。

## 7. 篇幅：150 行軟上限

超過 150 行的 skill，**要在檔頭寫明為什麼**。這是軟上限，不是禁令。

**為什麼是 150**：13 份實測呈雙峰——9 份落在 38～71 行，另一端是 142～255 行。
150 落在兩峰之間，會標記到 3 份（`scrum-master`、`qa-test-planner`、
`qa-automation-engineer`），而它們確實是流程最密的角色，寫得出理由就過。

**不寫會出什麼錯**：長度失控通常不是內容太多，而是**混進了不該在這一層的東西**。
`qa-automation-engineer` 曾有 386 行，其中 131 行是綁定技術棧的範例（見第 4 節）；
抽掉之後剩 255 行。上限的作用是讓這種混入被看見，而不是逼人刪內容。
